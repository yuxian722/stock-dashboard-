# bingomap 開發筆記

BINGO MAP補資料工具開發過程中踩過的坑跟確認過的規則，避免下次重複犯錯、
繞遠路。格式細節見`README.md`，這份文件記重要的「為什麼」。

## .strate格式的規則都是逆向真實檔案得出的，不是猜的

每一條規則背後都有真實範例檔案或截圖佐證（見`tests/`裡的測試案例跟
commit history），改動格式相關邏輯前，先確認有沒有真實資料支持，不要
憑直覺調整。目前已確認：

- **未上片的基板位置整筆省略**，不是留著寫`bin=0`——用真實檔案比對
  ROW×COLUMN理論滿版數 vs 實際筆數（TOTAL_BOND_DIE_QTY）反推出來的
- **LOC製程從1:1起編號，EPOXY製程從0:0起編號**——SOP文件明確警告這是
  最容易出錯、錯了會整批報廢的地方，兩種慣例不可混用
- CRLF換行、`[DIE_INFO_END]`後面固定兩個空行結尾——byte-for-byte驗證過
- DIE_INFO最後一欄不是恆定的`1`，是**層數**（見下面疊層那段）

## 疊層(一次上兩顆)：`[DIE_INFO_OTHER_LAYER_BEG/END]`

2026/08/14發現：機台一次動作同時吸取兩顆die疊在同一個基板位置時，
`.strate`檔案裡`[DIE_INFO_END]`後面會再接一段`[DIE_INFO_OTHER_LAYER_BEG]/
[DIE_INFO_OTHER_LAYER_END]`，裝另一層的資料，兩段DIE_INFO每列最後一欄
(層數)不同。這個結構在最初那份單層範例檔裡完全不會出現(尾欄固定`1`)，
是後來拿到雙層真實範例才發現的——**看到`f9`固定是`1`的樣本，不代表這個
欄位本來就是常數，只代表那份樣本剛好是單層。**

`blank_generator.py`/`assignment.py`目前都還只處理單層(`die_info`)，
`other_layer_die_info`還沒有對應的空白產生/填入邏輯——真的要補疊層資料
時要記得擴充這兩個檔案，不是只有`strate.py`的parse/write支援了就沒事。

（2026/08/14後續更新：`assignment.py`的`assign_two_layers()`跟webapp的
UI(疊層checkbox+主層/次層切換按鈕)都已經補齊，兩層各自獨立計數、各自
補滿才能產生檔案，已用真實雙層範例資料+Playwright端對端測試驗證過。）

**2026/08/17重大更正：`[DIE_INFO_OTHER_LAYER_*]`不是「每多一層就多一段」，
是「所有非目前層通通塞進同一段，靠每列自己的f9分辨層數」。** 之前只看過
單層跟雙層真實範例，順著雙層的結構猜測「三層以上大概是`OTHER_LAYER2`/
`OTHER_LAYER3`這樣一路加下去」——這次使用者提供一份真實的**8層**範例
(`tests/fixtures/2070_V25NVDY_F2006908_20260702203138.strate`)才發現
猜錯了：真實結構是`[DIE_INFO_BEG]`永遠只放f9最大(目前/最後完成)的那一層
(7筆，全部f9=8)，`[DIE_INFO_OTHER_LAYER_BEG]`一段就裝完剩下**所有**其他層
(49筆＝7層×7筆，照f9=1到7分成7組、每組內部substrate position順序跟
DIE_INFO一樣)。用每個substrate position在各層的timestamp反推出來的真實
上下料順序是「同一個位置疊完全部N層才換下一個位置」，但**檔案裡的列順序
是照f9分組**，不是照真實時序——這點只影響檔案怎麼寫，不影響
`assign_layers()`要不要模擬真實時序(不需要，跟原本1層/2層一樣用合成的
遞增timestamp即可)。

教訓：**看過2個資料點(單層、雙層)就對第3個資料點(3層以上)做線性外推，
一樣是没有真實證據的猜測**——這次算是猜對了大方向(還是同一組BEG/END
標記、還是靠f9分層)但猜錯了關鍵細節(段落數量 vs 分組方式)，如果沒有
使用者主動提供8層範例、而是直接照「每層一段」的猜測去實作，產生出來的
檔案格式會是錯的，而且不會有任何報錯提示——這正是本文件開頭那條原則
「格式細節都是逆向真實檔案得出的，不是猜的」要防的那種錯。

`assignment.py`已經加了通用的`assign_layers()`(N層，N=1就等同`assign_dies()`
的行為、N=2就等同`assign_two_layers()`)，`strate.py`完全不用改(它本來就是
逐列讀f9、沒有假設同一段內f9是常數，這個彈性當初寫的時候不是刻意預留的，
純粹是巧合寫對了)。webapp的UI也已經從「疊兩層」固定選項改成「疊幾層」
數字輸入(1~16)，已用這份8層真實範例做端對端驗證(parse回真實檔案、重新
`assign_layers()`產生、byte級比對兩邊`die_info`/`other_layer_die_info`一致)。

## Mapping SOAP服務(`mapping_service.py`)：母批號要去掉子批次尾碼

`http://tneas.tn.chipmos.com.tw:10000/Mapping/Service.asmx`的
`GetMappingLotNoByAssyLot`，傳入帶子批次尾碼的批號（例如`V32AWCW02`）
會回傳空結果——**即使那個子批次當下確實在產線上RUNNING**，也查無資料。
一定要先用`strip_sub_lot_suffix()`去掉尾碼（`V32AWCW02` -> `V32AWCW`）
才查得到。這個規則是連續測試了`V32AWCW01`、`V32AWCW`(第一次，沒查到)、
`V32AWCW02`才發現的——後來確認第二次測`V32AWCW`(去尾碼)其實有效，第一次
會失敗可能是別的原因，重點是**去尾碼的母批號查得到，帶尾碼的查不到**，
這是唯一穩定重現的規律。

同一份服務裡的`GetAOIBinData`，即使傳入正確格式(去尾碼)的真實批號，也
一律回`STATUS=NG`，判斷這支API不是wafer逐顆bin資料的來源，**已停損不要
再花時間猜它的參數**——這支API名稱雖然聽起來很像，但實測結果不支持這個
假設。

## DB vs ESEC(2100SD)：基板位置排列順序完全不同，不能共用一套邏輯

2026/08/14從PPT裡一封2019/11/27的內部信件截圖(第22頁)挖出來的：DB機台
跟ESEC 2100SD機台，即使是同一個產品、同一套SUBSTRATE_ROW/COLUMN，
DIE_INFO裡基板位置(第4欄)的排列順序完全不同：

- **DB**：從`0:0`開始，欄序由小到大，每欄內列由小到大遞增，單純掃描
- **ESEC**：從**最後一格**`COLUMN-1:ROW-1`開始，欄序由大到小，而且
  **每換一欄，列的方向就交替一次**(蛇形/boustrophedon)

信件原文直接寫：「以下畫面為DB&2100SD產生的BINGO MAP 啟始的位置相反,
所以如果COPY到不同機型的資料,所得的圖就會不同」——這不是理論推測，是
公司內部真實案例(BA708 MOVE OUT NG，補資料格式抄錯機型導致的異常)。

`blank_generator.py`的`machine_type`參數("DB"/"ESEC")就是照這個真實
比對寫的，兩組排列演算法各自用真實檔案的頭13筆資料驗證。**任何其他
機型(CM700等)在沒有真實範例驗證前，都不要假設沿用DB或ESEC其中一套
邏輯**——這兩套本身就已經證明「聽起來合理」不代表是對的(一開始设計時
完全没想到会有反向+蛇形这种排法)。

## wafer bin地圖的真正資料來源：反編譯.exe直接找到答案，不用猜

前面繞了很多路想找wafer bin地圖(WaferCoordinate.exe左邊那張綠/粉紅圖)的
資料來源——先猜過SOAP API(`GetAOIBinData`，已證實是死路)，後來使用者
一路找到`F:\SMAP\FRM\`這個資料夾，但一直卡在「不知道裡面檔案格式」。

2026/08/14換了個方法直接解決：**用`ilspycmd`反編譯`WaferCoordinate.exe`**
（`dotnet tool install -g ilspycmd --version 8.2.0.7535`，注意最新版
`ilspycmd`在這個環境裝不起來，要指定這個版本；另外執行時要
`export DOTNET_ROLL_FORWARD=LatestMajor`，因為這個版本的ilspycmd是針對
.NET 6打包的，這台機器只裝得了.NET 8 SDK，要讓它roll forward才跑得動）。
反編譯出來的`.cs`檔案裡，`DieAttachFmtRW.ReadMap()`跟`CMAP_I_HEADER`/
`CMAP_II_HEADER`/`CMAPBIN_I`/`CMAPBIN_II`這幾個class把FRM檔案的二進位
格式寫得一清二楚——欄位、byte數、大小端序都在裡面，不用再猜或等使用者
找範例檔案。詳細規格見`frm_reader.py`的docstring，這裡記重點教訓：

**遇到「不知道某個檔案格式」的問題，如果那個格式是由一支.exe寫出來/
讀進去的，且那支.exe是.NET程式（用`file`指令看到"Mono/.Net assembly"字樣），
第一步應該是嘗試反編譯，而不是先猜格式或一直伸手跟使用者要範例檔案。**
反編譯拿到的是100%正確的規格（除非程式本身有bug），比對照少量範例檔案
逆向猜測可靠得多，而且不需要使用者一直在現場翻檔案、來回傳截圖。

反編譯路上的坑：
- `ilspycmd`最新版(11.x)在這個環境`dotnet tool install`會失敗
  （"Settings file 'DotnetToolSettings.xml' was not found"），指定舊版
  `8.2.0.7535`才裝得起來
- 裝起來的`8.2.0.7535`是針對.NET 6打包的，這個環境只裝了.NET 8 SDK
  （apt套件庫沒有6.0/7.0 runtime），要設環境變數
  `DOTNET_ROLL_FORWARD=LatestMajor`讓.NET 8 runtime代跑.NET 6目標的程式，
  不然會報「You must install or update .NET to run this application」

## 移植使用者提供的參考工具：先分辨「活的邏輯」跟「死碼」，再談要不要搬

2026/08/14：使用者要求把另外兩套自己開發的ESEC 2100參考工具（STRATE座標偏移點除工具v78、
STRATE補檔工具v38）的功能也搬進bingomap網頁。這兩個檔案都是單檔HTML+內嵌JS，而且都是**改版多次
沒清乾淨**的狀態：

- v78裡有整個`run()`函式（連同只有它會呼叫的`renderCorrectWaferOverlay`/`diagnoseCoordModes`/
  `classifyRow`等一大串helper，約占全檔35%）完全沒被任何按鈕綁定——是作者放棄的舊版「比對兩張wafer
  MAP」設計，跟目前活的`v67*`/`v72*`/`v78*`是兩套不同的演算法，不是被依賴的helper
- v38裡有整段包在`<script type="text/plain" id="legacyV31">`裡的舊版`run()`實作——`type="text/plain"`
  的script瀏覽器根本不會執行，是100%死碼，而且檔案裡同一個函式名稱（如`mapHtml32`）還疊了3~4代
  舊定義，靠後面的`window.mapHtml32=function(){...}`覆蓋前面的，只有最後一次賦值是真的在跑

**移植前一定要先追蹤每個按鈕的`addEventListener`實際呼叫到哪個函式版本，把真正在跑的邏輯跟版本
演進留下的殘骸分開**，不要照著檔案從頭到尾的順序理解「這是什麼設計」，很容易把已經被放棄的舊設計
當成現行邏輯搬過來。

## 誤吸偏移／BIN點除：座標轉換公式是「現場驗證過的經驗公式」，不是幾何推導

v78的核心轉換（STRATE記錄的wafer座標`FX:FY`轉回原始wafer MAP座標）用固定X反轉：
`MAP_X = wafer_map裡實際資料的max_x - FX`，程式裡的中文註解直接寫「現場資料驗證後，回原始MAP採X
反轉」——這是作者拿ESEC 2100SD真實資料試出來的，不是從geometry第一性原理推出來的公式，而且**整個
工具鎖死只支援NOTCH=270**，其他角度直接不處理。

移植到`mispick_analysis.py`時比照辦理：只支援NOTCH=270，遇到其他NOTCH直接丟`UnsupportedNotchError`
拒絕分析，不要自己延伸公式去猜其他角度怎麼轉——這正是使用者當下提醒的：「他的是針對esec2100機台
開發所以會跟我的規則有點不一樣」，別把單一機型驗證過的經驗公式當成放諸四海皆準的通用邏輯。

同一個原因，這個分析流程本身**還沒拿bingomap這邊的真實已知誤吸案例核對過**（只有拿v78的公式手算
出的合成測資驗證過數學本身算對），操作前應該先用一個已知結果的真實案例試跑確認，不要一開始就直接
信任輸出拿去現場點除。

## 誤吸偏移分析讀的wafer MAP，跟FRM是同一種格式——但參考工具自己那段parser是用猜的，不要照抄

v78自己內建一個`parseWaferMapBinary`，是完全沒有固定header、用滑動視窗掃描位元組、每個候選區段用
「取樣80筆、要求≥85%像座標」這種機率門檻去猜出來的heuristic scanner，程式裡自己標註
`parser:'v56_viewer_4byte_col_rowhi_rowlo'`，註解也承認是「沿用使用者提供的wafer_viewer原圖parser」
——不是反編譯得出的，是猜的。這個位元組佈局（1 byte bin字元+2個0+2byte count+1個0接住座標，每筆座標
4 bytes：col、row高位、row低位、padding）跟`frm_reader.py`已經反編譯verified的FRM格式（bin_kind是
2-byte大端ASCII碼、格式I座標是1byte x+1byte y沒有padding byte）完全對不上。

問過使用者確認：誤吸點除工具讀的「原始wafer MAP」就是同一份F:\SMAP\FRM\的FRM檔案，所以
`mispick_analysis.py`直接吃`frm_to_wafer_bin_map()`轉出來的`WaferBinMap`，v78那段heuristic scanner
完全沒有搬——這是本專案「不要猜格式，能反編譯/能問清楚就不要用機率門檻硬猜」原則的又一次應用。

## 移植Crack模式時往回讀v78原始碼，才發現誤吸模式自己漏掉了wafer ID正規化

2026/08/14移植Crack位置回推時重新細讀`runV78Crack`，發現它比對wafer ID用的是
`String(r.strateWaferId||'').trim().toUpperCase()`——回頭看`runV68`（誤吸點除模式的進入點）
其實**也是**同一種寫法，只是我第一次移植`mispick_analysis.py`時只顧著搬座標轉換公式，
沒注意到這個正規化，寫成了`die.wafer_ring != wafer_ring`的exact match（比參考工具本身還嚴格，
會把大小寫或前後空白不同但其實是同一顆wafer的資料誤判成「其他wafer」而排除掉）。

已經修正：兩個模式現在共用`mispick_analysis.normalize_wafer_id()`（trim+大寫）做比對，
`crack_recovery.py`從一開始就用這個規則。**教訓：只移植看得到、在意的那一小段邏輯（例如這次
一開始只看了座標轉換公式那幾行）容易漏掉旁邊看起來不起眼但同樣重要的正規化/防呆邏輯——
移植同一個工具的第二個功能時，值得回頭把第一個功能也對照一次，不要假設第一次就搬乾淨了。**

## 誤吸偏移／Crack回推的座標公式：搬完ESEC工具之後才發現使用者實際用的是DB機型

2026/08/14：`mispick_analysis.py`跟`crack_recovery.py`都上線、也各自寫了測試跟通過Playwright
驗證之後，使用者才提醒：「記得我的基板上片strip規則跟wafer mapping座標規則是DB機型的」——這兩個
模組的座標轉換公式(NOTCH=270的X反轉、raw↔machine旋轉、輸出顯示的TX反轉、Crack局部分布的NOTCH
旋轉)全部是照ESEC 2100參考工具的程式碼字面搬過來的，而參考工具本身的註解也明講這些公式是「現場
驗證過的經驗公式」，只對ESEC 2100SD這個機型成立——**這兩個功能目前的座標數學，跟使用者實際在用的
DB機型規則很可能對不上**。

已經在網頁跟README/CLAUDE.md標上明顯警告，等使用者提供DB機台的真實案例(STRATE+wafer MAP+已知正確
結果)後重新推導公式。**教訓：移植別人給的參考工具時，工具本身是為哪個機型/情境開發的，不代表使用者
自己實際的生產規則也是同一個——即使工具程式碼裡寫死「這是驗證過的」，也只代表對工具原作者的情境
驗證過，換了使用情境（這裡是DB vs ESEC）還是要重新跟使用者核對，不能因為「反正是照抄現成驗證過的
公式」就跳過這一步。**跟blank_generator.py的DB/ESEC基板排列規則不是同一件事——那邊已經支援machine_type
參數且DB是預設值；這裡誤吸/Crack的座標轉換公式是全新的、只依照ESEC工具本身的假設寫的，兩者不要混為
一談。

**2026/08/17後續更新：使用者提供了DB機型的真實案例，問題已解決。** 證據是四張截圖+一個真實
`.strate`檔案：(1) ChipMOS內部「WaferCoordinate」工具的截圖，機型選單明確選在「DB系列」，右側面板

## 正則式抓XML標籤配對，一定要處理自我封閉標籤，不然會靜默漏資料

2026/08/19開發SECS格式化參數(`secs_params.py`)時發現、修好一個同時存在於`secs_log.py`跟
`secs_params.py`的bug：兩邊的`_TRANSACTION_RE`原本是`<Transaction\b[^>]*>.*?</Transaction>`，
沒考慮到SECS log裡每個Request那半都是自我封閉標籤`<Transaction ... />`（內容本來就是空的）——
`[^>]*>`會把`/>`誤認成一般開始標籤的`>`，接著非貪婪的`.*?</Transaction>`就一路吃到**下一個**
Transaction的結束標籤才停，把兩個不相干的Transaction黏成一段無效XML，`ET.fromstring`解析失敗、
兩個都被跳過——**沒有任何錯誤訊息，表面上看起來像是「這個Transaction沒被記錄」，不會有任何跡象
顯示是解析器本身把資料吃掉了**。

之所以拖到現在才發現：平常log裡一個Request跟它自己的Reply中間，通常還夾著其他Transaction(有自己
的結束標籤，讓正則式提早停下，不會誤吃)，所以大多數情況下這個bug不會發作、東西看起來解析得好好的。
真實log裡第二次S7F25快照(TID=58203)剛好是Request後面緊接著自己的Reply、中間沒有別的Transaction，
才踩中——如果不是順手拿真實log核對「應該有2筆快照，API卻只回傳1筆」這種已知數量的落差，這個bug可能
會一直潛伏下去。

修正：`<Transaction\b[^>]*/>|<Transaction\b[^>]*>.*?</Transaction>`——用兩個alternative，先試著
把整個自我封閉標籤當一個完整、獨立的match（不需要找配對的結束標籤），第二個alternative才是原本的
「找配對結束標籤」邏輯，只會在標籤真的不是自我封閉時才用到。

教訓：**這個專案處理的XML/類XML格式(SECS log、FRM二進位、.strate文字格式…)幾乎都不是標準工具能
直接餵進去驗證的半成品格式，常常要靠手寫正則式/位元組掃描去抓——這類手寫parser的正確性驗證，光看
「有抓到資料、數量看起來合理」是不夠的，因為漏資料可能完全不報錯、看起來一切正常。真的要驗證，要
拿一個已知的真實數量（這裡是「log裡到底有幾次S7F25快照」）主動去核對，不能只驗證抓出來的那幾筆
資料本身格式對不對——格式對不代表沒有漏掉別的筆數。**

## T點公式從頭到尾是巧合，不是真規則——反編譯真正的.exe才發現這件事本身可以直接驗證

2026/08/14的T點調查（見`webapp/README.md`「T點標示」章節）靠著使用者一輪一輪回報真實照片，最後訂出
公式`T點 = (columns//2 - reference_point_x, 0)`，用一片真實wafer(AW191 layout)驗證算出來的座標剛好
對上使用者回報的位置，當時信心給得不低。**2026/08/19用另一片wafer(EU014 layout)測試才發現這個公式
從一開始就是錯的、能算對純粹是巧合**——不是「這片layout不適用」這種漸進式失效，是整個公式的立論基礎
（`reference_point_x`/`y`欄位會被畫成T點標記）根本不成立。

發現方法：使用者這次直接提供了`WaferCoordinate.exe`本尊（連同`.pdb`），比照Phase 3的做法用
`ilspycmd`重新反編譯——但這次不是為了搞懂檔案格式（FRM格式本身早就解決了），是為了搞懂「畫面上那個
T點紋路記號到底是怎麼畫出來的」。全文搜尋反編譯出來的C#原始碼，找到`ReferencePointX`/
`ReferencePointY`只在`DieAttachFmtRW`裡被讀取、賦值，**完全沒有在任何`Draw*`函式或畫面繪製邏輯裡被
引用過**——真正的WaferCoordinate.exe根本不會拿這兩個欄位畫任何東西。之前公式能對上，只是因為那一次
巧合算出的座標剛好符合使用者實際觀察到的位置，不是因為抓到了真正的規則。

同一次反編譯還連帶找到一個真正會影響畫面方向的機制：`InitMap()`會讀取`F:\SMAP\MAP\<layout名稱>`
（不是FRM檔案本身，是另一個獨立檔案），找`Flat=`那一行的角度值(0/90/180/270)來決定要不要旋轉畫面
——這才是「鏡像」問題真正可能的成因，跟`ReferencePointX/Y`完全無關。這次案例最後排除了旋轉問題
（使用者確認那個MAP檔案根本不存在，且逐格核對FRM資料跟真實截圖完全吻合，沒有鏡像），但如果之後又
遇到方向不一致的回報，`Flat=`這個機制才是該查的地方，不是`reference_point_x/y`。

使用者事後說明T點真正的來源：「以中心線的T點位置跟bin7及bin1行列去比對出來」——操作員自己拿
WaferCoordinate.exe畫面上那條**純幾何、寫死在畫面正中央、跟資料完全無關**的十字參考線
（`DrawGrid()`畫的），搭配bin7/bin1格子肉眼比對出來的，**每片wafer都要重新判斷，不是任何欄位可以
算出來的常數**。已經把①補資料頁、②誤吸偏移頁的T點都改成手動輸入(選填)，不再顯示自動算出來、可能
是錯的標記。④STRATE補檔頁的`SECS_T_POINT`(套用到整份log全部10片wafer)還沒有比照修改，是已知的
後續工作——那個值本身是操作員真的觀察出來的沒錯，但「同一份log全部wafer共用同一個T點」的假設，
現在看來也站不住腳（既然每片wafer都要操作員各自判斷，就不該是layout常數）。

教訓：**光是「用真實資料驗證過一次、算出來的座標對得上」不代表抓到了真正的規則，可能只是公式剛好
在那個案例上算對——尤其是像T點這種「反編譯找不到對應繪圖邏輯」的情況，代表這個值很可能根本不是
軟體算出來的，是操作員的人工判斷。遇到「同一個工具，換一筆真實資料就對不上」的回報時，不要急著
在原本公式上加修正項或猜第二種情況的公式，應該回頭確認一開始「這是不是真的由資料決定」這個前提
本身有沒有問題——這次靠重新反編譯真正的.exe原始碼直接找到答案，比再猜一輪公式快得多，也不會像
之前SECS log/FRM那幾次T點調查一樣來回猜好幾輪。**

2026/08/18做「④STRATE補檔 XML合併」(從SECS log直接救回`.strate`檔案)時，`bingomap/secs_log.py`的
docstring寫著`DIE_INFO`的`<Item>`「ALREADY in the exact 9-field CSV format .strate DIE_INFO lines
use...DieInfo.from_line() parses them completely unchanged」，而且用使用者提供的一份真實`.strate`
參考檔案做了「逐行byte-for-byte比對，完全一致」的驗證，信心給得很高。**2026/08/21發現這個驗證本身
就是錯的**：使用者拿這份`.strate`(`2070_V30EUC6_...`)在①補資料頁當範本載入、疊在WPQ5310156SS/FC2643
真實wafer上，「已寫入」的座標散得到處都是，一度以為是wafer圖鏡像了。

真正查下去才發現：`wafer_xy`欄位的兩個數字，log自己記錄的順序是`row:col`(列在前)，但`.strate`檔案
格式本身的約定是`col:row`(欄在前，2026/08/17另一片完全不同的真實DB案例驗證過的)——`extract_strate_files()`
把log的`DIE_INFO`原封不動複製出去，語法(9欄CSV)完全對，但**欄位語意**(每個數字代表哪一軸)反了。
那次「逐行byte-for-byte比對完全一致」的驗證，比對用的參考`.strate`檔案，本身也是同一套方法產生的
(同樣沒做欄位互換)——兩邊「一致」只是同一個錯誤的兩份拷貝，根本沒有驗證到跟機台原生`.strate`格式
是否相符。

發現的過程本身值得記錄：不是重新猜座標公式，而是直接拿這份`.strate`裡FC2643的49顆die座標，逐顆去
比對FC2643**真正的`.frm`檔案**(die_map，跟`.strate`來源完全獨立)——原封不動比對只有35/49(71%)對得
上真實bin=1的位置，其餘8顆完全落在wafer外圍空白、6顆對到錯誤的bin；把兩個數字互換之後，49/49全部
對到bin=1、互不重複，跟`.strate`自己記錄「全部是良品」完全吻合。這個交叉比對比「跟另一份同來源的
`.strate`比對」有意義得多，因為`.frm`是完全獨立的第三方資料，不可能跟log的錯誤同步出錯。

已修正：`_swap_wafer_xy()`把`extract_strate_files()`輸出的`wafer_xy`從log原生的row:col換成`.strate`
標準的col:row；`wafer_map_from_element()`的`WaferBinMap`內部存法、`strate_xml.js`的`renderWaferGrid()`、
硬寫死的`SECS_T_POINT`常數也都跟著同步訂正(細節見`webapp/README.md`「STRATE補檔 XML合併」章節
2026/08/21的更正)。新增的回歸測試直接用真實`.frm`(不是另一份`.strate`)當獨立驗證來源，鎖定這次的
發現不會再退回去。

教訓：**「拿另一份看起來相關的真實資料逐行比對、完全一致」不等於「驗證過格式正確」——如果兩份資料
是同一套流程/同一個人/同一次操作產生的，很可能共享同一個系統性錯誤，比對出「一致」只是確認了兩份
拷貝真的相同，沒有檢查這個「相同的內容」本身對不對。要驗證一個轉換/欄位語意，必須拿**完全獨立、
不同生成方法**的真實資料反過來交叉核對(這次是反過來查真正的`.frm`檔案，而不是繼續比對另一份
`.strate`)，才可能抓到「語法對、語意錯」這種比對本身抓不出來的問題。這跟T點公式那次的教訓是同一個
根源(見前面「T點公式從頭到尾是巧合」那則)：驗證方法本身有沒有真的獨立、有沒有可能循環論證，比
「驗證過一次」這件事本身更重要。**

## 後續更正：上面的swap結論整個是錯的——兩個獨立、方向相反的欄位語意bug疊在一起，互相抵消才通過了驗證

2026/08/26使用者回報①補資料頁用STRATE補檔救回來的檔案，已寫入的座標又跑到wafer外圍了——這次使用者
一次給了兩份完全獨立的真實資料：同一台machine對同一枚基板(`Z25709007096`)產生的真實log
(`BAB1420260801_04.0.log`)**跟**真正的`.strate`檔案，兩者可以直接互相比對，不用像上面那則一樣繞道
去查`.frm`。結果非常清楚：log的`StrateMap`交易裡`<DIE_INFO>`/`<DIE_INFO_OTHER_LAYER>`的224行(56+168)
`<Item>`文字，跟真正`.strate`檔案自己的DIE_INFO逐行**完全一致，一個字都沒有不一樣**——`wafer_xy`本來
就已經是`.strate`格式的`col:row`，上面那則(「STRATE補檔頁的wafer_xy欄位順序反了」)做的`_swap_wafer_xy()`
從頭到尾是不需要的，而且是**有害的**：把本來就對的資料又轉了一次，變成錯的。

但上面那則的`.frm`交叉比對(49顆FC2643的die，互換後49/49對到bin=1)明明也是真實資料驗證，為什麼還是
得出錯誤結論？因為那個驗證本身混進了**第二個、方向相反的獨立bug**：`frm_reader.py`解析FRM二進位格式
時，把讀到的兩個座標位元組叫做`x, y`存進`die_map[(x,y)]`——但這兩個變數命名本身就是誤導，第一個位元組
實際上是row(列)、不是col(欄)。也就是說`frm.die_map`真正的key其實是`(row,col)`，不是變數名稱暗示的
`(col,row)`。「不轉wafer_xy、但用`frm.die_map.get((row,col))`查」是對的；但當時的驗證是「轉了
wafer_xy、然後用`frm.die_map.get((col,row))`查」——兩個獨立的方向相反錯誤疊在一起，數學上剛好互相
抵消，讓swap之後的結果「看起來」完全通過了驗證(49/49對到bin=1，一個都不重複)，實際上是兩個錯的東西
湊出一個巧合的對。連`wafer_map_from_element()`(BinList解析)也發現同樣的模式：log的`<ColCount>`/
`<RowCount>`標籤本身也跟`.strate`的col/row軸向對調(`ColCount`=46其實對應`.strate`的row軸長度，
`RowCount`=24對應col軸長度)——SECS log這整個資料來源，欄位名稱(`x`/`y`/`ColCount`/`RowCount`)本身
不可信，只有拿真實(log,`.strate`)或(FRM,`.strate`)這種**跨資料來源**的直接比對才靠得住。

已修正：`_swap_wafer_xy()`整個刪除，`_die_list()`直接使用log原始的`wafer_xy`不做任何轉換；
`wafer_map_from_element()`的`ColCount`/`RowCount`對調處理、`BinList`的chunk索引/字元位置對調處理。
新增的回歸測試直接用「真實log」vs「真實.strate」逐行byte-for-byte比對，這是比之前「swap後對到FRM
bin=1」更直接、更不會被第二個獨立bug污染的驗證方式——不透過任何中間轉換或查表，兩份獨立產生的真實
資料直接比對逐字相符，沒有任何可以讓兩個bug互相抵消的空間。

教訓：**兩個獨立的欄位語意bug，只要方向相反，套用在同一份資料上就會互相抵消，讓其中一個(甚至兩個)
看起來都通過了「跟真實資料比對」的驗證——這是比「參考資料本身也有同一個錯」(上面那則的教訓)更隱蔽
的陷阱，因為這次交叉比對用的`.frm`檔案是真正獨立的第三方資料，理論上「應該」足以抓到問題，實際上
卻因為驗證鏈路中還有另一個環節(這裡是`frm_reader.py`的die_map key順序)也帶著錯，讓兩個錯正好互相
掩護。避免這個陷阱的關鍵是**盡量縮短驗證鏈路、減少中間環節**：與其「A轉換過的結果」去比對「B查表
出來的結果」(兩邊都可能各自帶著自己的錯)，不如直接比對「A的原始輸出」跟「C的原始輸出」(兩份完全
獨立、沒有經過任何己方轉換的真實資料)，中間環節越少，能藏兩個互相抵消的bug的空間就越小。**

新設計重做，通常比繼續猜測「這次補哪裡才對」更快，也更不容易第四次被打回票。**

## `frm_reader.py`的`die_map` key順序bug：診斷出來之後，因為顧慮T點公式而暫時擱置，結果過了幾天被另一個症狀重新撞上

2026/08/26調查SECS log的`wafer_xy` swap問題(見上面「後續更正：上面的swap結論整個是錯的」那則)時，
已經用49顆FC2643真實die正確診斷出`frm_reader.py`的`frm.die_map`存在同一種問題：解析FRM二進位格式時
把兩個座標位元組叫做`x, y`存進`die_map[(x,y)]`，但這個命名本身是誤導的，真正的key其實是`(row,col)`。
當時只修了SECS log這一側(刪除`_swap_wafer_xy()`、修正`wafer_map_from_element()`的`ColCount`/
`RowCount`)，`frm_reader.py`自己的`die_map`/`frm_to_wafer_bin_map()`留著沒動——因為`frm.col`/
`frm.row`這兩個欄位本身已經被T點公式(`columns−Ref.Y`/`rows+Ref.X`)獨立驗證過，當下判斷「貿然對調
怕連T點也跟著壞掉」，選擇先擱置。

2026/08/27使用者在②誤吸偏移／BIN點除頁把角度轉成90°，回報「18:4那一顆顯示bin7，我實際作業是顯示
bin1，開發軟體的bin6跟機台的圖無法對起來」。第一版回應判斷「旋轉本來就會讓不同的die佔到同一個顯示
座標，bin不同是預期行為」——使用者直接糾正這個判斷的物理前提本身就是錯的：「機台上的bin code跟即使
轉方向bin code是不可能變，bin7就是粉紅色，bin1就是綠色」，並指示回頭查SECS log跟`.strate`
(`Z25709007096`)的`WaferUpload`/`WAFER_INFO`資料重新核對。

照指示重新交叉比對，這次多了一個之前沒做過的獨立來源：拿同一片wafer已經修正過的SECS-log-derived
wafer map反過來對FRM-derived wafer map，854顆die裡不對調只有44%座標空間對得上、對調後98.8%對得上
(89.6%連bin值都一致，跟`.strate`原本就有的記錄時間差重新分類率同一量級)——連同已有的49顆die跟
PickDie時間戳反推公式，三個獨立來源方向一致，這次才真的動手修了`frm_to_wafer_bin_map()`：`die_map`
的raw key`(a,b)`查表時對調成`(b,a)`、回傳的`WaferBinMap`的`columns`/`rows`對調成`frm.row`/`frm.col`。
`frm.col`/`frm.row`欄位本身(header讀出來的原始值)刻意保持不動，`webapp/app.py`回傳JSON的

`columns`/`rows`去框)，避免波及已驗證過的T點公式——細節見`webapp/README.md`「STRATE補檔 XML合併」
章節2026/08/27的更正記錄。

教訓：**「已經正確診斷出問題」不等於「已經處理掉了」，尤其是像這次因為另一個顧慮(T點公式)主動選擇
暫緩修復的情況——擱置的已知問題如果沒有明確的後續排程，很容易在下一次表面上看起來完全不相干的
症狀報告(這次是「旋轉後bin對不上」，而不是「STRATE補檔座標跑出wafer外」)裡才會被重新想起，中間
的使用者體驗成本(這次是又一輪「你的解釋不對，回頭查證據」的來回)其實是可以避免的。發現一個bug
但決定不修時，至少要留下清楚的紀錄講明白「為什麼沒修、擔心什麼」(這次CLAUDE.md/README.md都有記
到這個顧慮)，這樣至少下次重新處理時能直接對症下藥、不用重新從頭診斷一次。**

## `.strate`的`wafer_ring`欄位是逐顆die各自記錄的，不是整份基板共用一個值——之前一直假設是後者

2026/08/27使用者回報：把Z25709007096這份.strate當範本載入①補資料頁，畫面上顯示這枚基板「有兩片wafer
id FCEEB7/FC2643」，應該要出現兩片wafer的圖跟分布位置，但只出現一片。

追查發現這個假設本身就是錯的，錯在兩個地方：
1. `webapp/app.py`的`_substrate_summary()`只取`sf.die_info[0].wafer_ring`當作整份基板唯一的
   wafer_ring，`_substrate_die_positions()`把`die_info`跟`other_layer_die_info`的座標全部攤平成
   一個清單，完全沒有保留每一列自己的wafer_ring
2. `webapp/static/app.js`的`loadTemplate()`更明確地寫著「a .strate file carries no notion of
   which physical wafer panel a die came from」，所以無條件把每一顆讀進來的pick指派成panel 0

實際去查`DieInfo`的欄位定義(`bingomap/strate.py`)，`wafer_ring`從一開始就是`(index,wafer_ring,
wafer_xy,sub_pos,bin,f6,f7,timestamp,f9)`這9個逐列欄位之一，不是檔頭的整份基板常數——用真實的
Z25709007096檔案實際统计才發現，這份基板的224顆die(56顆die_info+168顆other_layer_die_info)裡
**同一層(同一個f9)內部就同時混著FC2643(每層12~13顆)跟FCEEB7(每層43~44顆)兩片物理wafer**，不是乾淨的
「第1層算一片wafer、第2層算另一片」——這代表就算之前用「每層對應一片wafer」的方式去分配panel也是錯的，
必須逐顆die照它自己的wafer_ring分配，沒有更簡單的規律可以走捷徑。

已修正：
- `_die_info_to_picks()`把每顆die自己的`wafer_ring`一起帶出去(見它的完整docstring)，不再只在
  `_substrate_summary()`那層取第一顆的值
- `app.js`的`loadTemplate()`改成先掃過所有pick蒐集出現過的wafer_ring(照第一次出現的順序)，剛好兩種
  的話自動開啟「跨兩片wafer」、逐顆die照自己的wafer_ring分配panel 0/1(不是整層分配)；超過兩種的話
  (目前介面只能表達2片)全部先歸在panel 0並在狀態文字裡明確警告，不假裝處理得了；剛好一種(最常見的
  單一wafer情況)行為跟以前一樣全部panel 0
- 順便驗證了`wafer_ring`(如FC2643/FCEEB7)就是FRM的Barcode ID、`.strate`自己的`mapping_lot`就是FRM
  的LotNo(這次用的正是這個專案一路驗證下來的WPQ5310156SS/FC2643這組真實資料交叉確認)，所以載入範本
  時順便把兩片panel的FRM Lot No/Barcode ID都自動填好，使用者各自按一次「自動讀取FRM檔案」就能把兩片
  wafer的圖都叫出來，不用手動查/打這兩個欄位
- 過程中抓到一個相關的小bug：panel 0(靜態HTML)的FRM Lot No/Barcode ID欄位原本有一組開發時期留下的
  預設值(`8P065800A1`/`T3DA62`)，第一版修正用「欄位是空的才填」當防呆條件，結果被這組非空的舊預設值
  擋住、填不進去——跟其他所有範本欄位(assy_lot/mapping_lot/...)一樣直接無條件覆蓋才對，範本載入本來
  就應該讓範本自己的資料說了算，不需要顧慮「使用者可能手動填過」這種在其他欄位從來沒有的假設
- Playwright實際載入真實的Z25709007096範本＋真實FC2643 FRM檔案驗證：224顆pick正確拆成49(FC2643)+
  175(FCEEB7)兩組、`multi_wafer_enabled`自動勾選、兩片panel的LotNo/Barcode ID都正確填成
  `WPQ5310156SS`+各自的wafer_ring、FC2643那49顆pick座標全部落在該片真實wafer範圍內(x:0-23,y:0-45)
  沒有跑出界外
- 新增後端回歸測試`test_api_parse_strate_picks_carry_the_real_per_die_wafer_ring_not_a_single_value`：
  直接用這份真實檔案鎖定每一層都真的混著兩片wafer(不是乾淨的per-layer切法)，避免以後又退回「一層一片
  wafer」的簡化假設

教訓：**跟前面「die_map key順序命名誤導」是同一種陷阱的變體——這次是「以為某個資料格式沒有記錄某項
資訊」，但實際上資訊就在那裡(`wafer_ring`一直都是逐列欄位)，只是程式一路以來都只取第一筆代表全部，
沒人质疑過「這樣夠嗎」。遇到「這個檔案格式應該無法回答X」的假設時，值得先去翻一下格式定義本身(這裡是
`DieInfo`的dataclass欄位)確認是不是真的沒有，而不是直接把「目前程式沒有用到它」當成「格式裡本來就沒
有」。**

## 誤吸偏移頁的機台偏移量拒絕0——這個限制本身沒有真實依據，只是最初設計時沒想到0該被允許

2026/08/27使用者回報「機台偏移量」欄位跳過0(從1直接跳到-1)：「如果T點沒有偏當然就是0，T點偏移才會有
(1:0)(-1:0)(0:1)(0:-1)」。查出`mispick_analysis.py`的`make_offset()`從一開始就寫死拒絕`value == 0`，
`mispick.js`的方向微調按鈕也配合這個限制，算出0時強制改回±1——但`Offset.axis`只用來顯示，分析邏輯
(`_classify_row()`)只吃`offset.dx`/`offset.dy`，value=0時dx=dy=0，等於「不偏移」的identity情況，
本來就是分析邏輯可以正常處理的一種狀態，這個限制找不到真實資料或案例佐證，純粹是最初「反正要分析就
一定要有偏移量」的假設。已修正：拿掉`make_offset()`的0限制、`nudgeOffset()`的強制跳過0邏輯，
表單標籤跟預設值也一併訂正。順便照使用者的要求把「①原始 wafer MAP」的T點預覽改成同時畫兩張圖(左圖
T點固定不套偏移、右圖套用目前偏移量即時重畫)，方便直接比對偏移前後T點落在哪裡。細節見
`webapp/README.md`「誤吸偏移頁：機台偏移量要能是0」章節。

教訓：跟上一則同一個模式——**「一個值被程式拒絕」不代表這個值本身沒有意義，可能只是最初設計時沒想到
該被允許，遇到使用者說「這個值應該要能選」時，先查這個限制有沒有真實依據，不要預設是刻意的安全防呆。**

## 「金邊朝下」機台的BINGO MAP座標——查了真實資料才發現不需要改，是下游報表工具自己在轉，不是我們的檔案

2026/08/27使用者提出：「我機台的基板作業是金邊朝下，而bingomap圖檔的畫面是金邊朝上，所以我的機台的
基板作業畫面會跟bingomap差180度，strate檔案的作業（0:0）也會轉成180度，你思考一下這樣圖檔才會一樣」
——並附上兩份佐證：(1)ChipMOS內部真實「Bingo Map Query」報表(Strip ID Z26306101253，Pass 299/Fail 9，
9個壞點座標標在G9/O6/P6/H10/G10/I10/I11等格子)；(2)一份SOP教材頁面，明確寫著「金邊方向都朝上」是
先前另一個真實案例(L10AWKI01)驗證過、不需要翻轉的基準情況。

這個問題不能用猜的——上一版(見前一則「一個值被程式拒絕」的教訓)靠的是先前SOP頁面的「金邊朝上」驗證，
現在使用者說他的機台是反過來的「金邊朝下」，如果貿然照「180度」的說法把`blank_generator.py`的
`sub_pos`欄跟列都點對稱翻轉，一來不確定「180度」是真的兩軸都翻轉還是只有其中一軸(物理上把一片扁平
基板「翻面」，其實只會翻轉其中一個軸，不是像旋轉照片那樣兩軸都轉)，二來也不確定會不會反而弄壞前面
已經驗證過的「金邊朝上」情況。所以要求使用者提供這片金邊朝下、真正確認過的Strip ID(Z26306101253)的
真實SECS log，才能像這個專案一路以來的做法一樣，拿真實資料交叉比對，不是拿猜的公式硬套。

使用者提供了`BAA0820260814_07.0.log`(真實log，含這枚Strip ID的StrateMap交易)。決定性的比對：

1. **真實DIE_INFO的填入順序，跟`generate_blank(machine_type="DB", convention="EPOXY")`現有(完全沒改過)
   產生的順序逐格一致**——把log裡實際缺席的9個位置(NG/未上片，本來就整筆省略，見本文件最上面那條規則)
   從`generate_blank()`預測出來的順序裡拿掉之後，剩下299個位置的順序跟真實log完全一模一樣，一個都
   沒有錯位
2. 另外把這9個缺席位置換算成Bingo Map Query自己用的英文字母欄(A~AB)+數字列(1~11)標籤，發現只要把
   「列」反過來(`列標籤 = 總列數 − 0起算的列`)，欄(字母)完全不用動，9個**全部**精確對上Bingo Map
   Query報表上的壞點標籤(`G9、G10、H10、I10、I11、O6、P6、Y5、AA11`)——一開始只確認8/9是因為第一張
   照片模糊、Y跟AA兩個欄位長得像分不清楚，使用者後來補了一張清楚的截圖，才把第9個(Y5)也對上，變成
   9/9全部吻合，不是只有8個

**結論：`blank_generator.py`完全不用改，這不是我們檔案產生邏輯的bug。** `sub_pos`欄位記錄的是機台
自己內部固定的座標系統，跟「當天金邊朝哪邊」完全無關，同一套DB/EPOXY規則不管金邊朝上或朝下都是對的
——「Bingo Map Query」這個下游報表工具自己在顯示的時候，額外做了一次跟座標方向有關的欄位轉換(很可能
只轉了「列」，沒有連「欄」一起轉，因為物理上「翻面」本來就只會反轉其中一軸)，這是報表工具自己的
顯示邏輯，不是我們產生/救回`.strate`檔案應該要模仿的東西——我們的責任是重現機台真正寫出來的原始
座標，不是重現Bingo Map Query的人類可讀畫面。

已把這個真實Strip ID的log存成回歸測試的fixture(`tests/fixtures/BAA0820260814_07_Z26306101253.log`)，
`tests/test_blank_generator_gold_edge_orientation.py`鎖定「真實log的DIE_INFO順序跟`generate_blank()`
現有輸出逐格一致」這個結論，以後如果有人真的想「修」這個金邊方向問題，這個測試會先擋下來提醒不要
亂改。

教訓：**使用者一開始描述的症狀(「跟bingomap圖檔畫面差180度」)聽起來像是我們的程式需要修正，但深入
查了真實資料才發現：問題其實出在別的系統(下游報表工具)身上，我們自己的邏輯從頭到尾都是對的。這是
「先查證、不要照描述直接動手改」這條專案鐵律的又一次體現——如果當初只憑使用者的文字描述就去改
`blank_generator.py`，很可能會把原本正確的邏輯改壞，而且使用者自己也沒辦法從症狀本身分辨出問題到底
出在我們的工具、還是出在他比對用的另一個系統。堅持要求提供可以交叉比對的真實資料(這次是log檔案)，
不但避免了誤改，還意外查出真正的成因跟我們原本以為的完全不同。**

### 後續更正：「檔案資料不用改」是對的，但漏了「畫面顯示也要能跟Bingo Map Query對得起來」這個使用者真正在意的點

上面那則的結論本身沒有錯——`.strate`檔案、`generate_blank()`寫出來的`sub_pos`資料確實不需要改，這點
已經用真實資料證明過。但使用者接著追問「為什麼不需修改，我不是有給你看軟體跑出來的bingomap圖跟機台的
實際圖檔不一樣」——這句話點出一個我當時沒接住的區別：使用者從頭到尾在意的是①補資料頁上**畫面顯示**
的BINGO MAP格子圖，跟Bingo Map Query/機台實際畫面**看起來不一樣**，不是`.strate`檔案內容本身錯不錯。
「檔案資料是對的」跟「畫面顯示看起來一樣」是兩件不同的事——我只驗證了前者，就直接回答「不用改」，
沒有意識到使用者的原始抱怨其實是在講後者。

回頭看`webapp/static/app.js`的`renderSubstrateGridInto()`：BINGO MAP格子圖畫面永遠是「列(row)由小到大
由上到下」直接畫原始`sub_pos`的列數字，沒有任何轉換——而Bingo Map Query顯示同一份資料時，會把列反過來
(`列標籤 = 總列數 − 0起算的列`，見上面那則的9/9驗證)。這代表：即使兩邊底層座標資料完全相同，我們畫面
上的BINGO MAP格子圖跟Bingo Map Query的報表圖，視覺上看起來就是上下顛倒的——這正是使用者第一次拿兩張
截圖並排給我看時，肉眼看起來「不一樣」的真正原因，不是資料錯，是顯示順序沒有對齊。

已修正：①補資料頁新增一個純顯示用的勾選框「BINGO MAP列(row)方向跟Bingo Map Query/機台實際畫面一致」
(預設不勾選，維持原本行為)——勾選後，畫面上列的排列順序整批反過來、列標籤數字也換成跟Bingo Map Query
一致的「總列數−0起算的列」，但每一格的`dataset.pos`(真正的col:row，點擊/反查/CSV/實際產生的.strate
檔案都是用這個)完全不受影響，純粹是重新排列畫面上哪一列出現在哪個垂直位置。用Playwright驗證過：勾選
前後底層座標集合完全一致，畫面列順序精確反轉，列標籤數字正確對應Bingo Map Query的編號方式。

教訓：**「使用者給我看的兩張截圖看起來不一樣」這個症狀，可以同時有兩個層次的答案——「底層資料對不對」
跟「畫面呈現方不方式一樣」——只回答其中一層、卻用「不用改」這種聽起來涵蓋全局的措辭去結案，會讓使用者
覺得自己明明給了證據卻被忽略。這次的教訓不是「不該去查資料」（查資料本身是對的、也查到了真正有用的
發現），而是「查完之後要回頭對照使用者最初給的證據，確認每一個他實際展示過的現象都有被交代到，不能
證明了A就直接宣稱整個問題都解決了」。**

### 再後續更正：第一版的顯示修正本身又犯了同一種錯——把列標題換成「推算出來的號碼」，反而製造出新的「畫面數字對不上檔案」問題

上一版加的勾選框，除了把畫面上「哪一列排在上面/下面」反過來，還順手把列標題的**數字本身**也換算成
`總列數−真正的row+1`(想讓標題數字跟Bingo Map Query的編號一致)。使用者馬上抓到問題：「這樣我檔案
state 0:0，0:1跟你的軟體bingo map跑出來的座標位置不一致」——螢幕上某一列標題印的數字，變成一個
**推算出來、不是那一列真正row值**的號碼，跟同一列裡每一格title顯示的真正`col:row`兜不起來，反而比
不勾選還容易搞混：使用者盯著標題數字，沒辦法直接對應回`.strate`檔案自己記錄的座標。

已修正：拿掉列標題的換算，勾選框現在**只**決定「哪一列排在畫面上方/下方」，列標題(跟每一格的
title/pos)不管有沒有勾選，永遠顯示那一列真正的row值——跟`.strate`檔案自己的`0:0`、`0:1`直接一致。
這樣畫面的整體「形狀」還是能對上Bingo Map Query(因為排列順序反過來了)，但螢幕上任何一個數字都不會
是編出來的，使用者隨時可以直接拿螢幕上印的數字去對檔案內容。

教訓：**這是同一次調查裡連續第二次犯「只解決了字面上提到的需求、沒有推演使用者真正在意的東西」這種
錯——上一次是「只改T點標記、沒改整片圖形」，這次是「為了讓標題數字看起來跟Bingo Map Query一致，
自己發明了一個新號碼，卻犧牲了『畫面數字必須跟檔案座標一致』這個更基本、使用者從來沒說出口但顯然
更重要的前提」。牽涉到座標/標籤顯示的改動，優先順序永遠是先確保「畫面上看到的數字＝檔案裡真正的
數字」這條底線不能破，其他像是「形狀要跟參考畫面一致」這種錦上添花的需求，要在不violate這條底線的
前提下另外想辦法達成(這次是靠純粹的排列順序，不用動任何標籤數字)。**

教訓：**跟前面兩則同一次調查、但方向相反的提醒——不是每個座標顯示問題都要做成保守的勾選框。前兩次

畫蛇添足——多一個預設關閉的選項，等於讓「錯誤的畫法」繼續是預設值，使用者還要自己記得每次都去勾選。
分辨「這是尚待驗證、需要保守處理的情況」還是「已經确认是bug、應該直接修正的情況」，要看使用者的語氣

### 再後續：BINGO MAP格子圖上「強制點除」的紅框會被同一個位置另一層的判定悄悄蓋掉

使用者拿②誤吸偏移頁一枚真實疊層基板(Z25709007096，最多4層堆疊在同一批56~60個基板位置上)測試，
文字結果正確顯示「強制點除 2」，但BINGO MAP格子圖畫面上完全找不到紅框，回報「強制點除應該會出現
紅色框框在bingomap圖檔內，這樣我不知道是哪一顆」。

查出原因：`mispick.js`的`renderSubstrateGrid()`把`sub.grid_cells`直接建成`new Map(grid_cells.map(c =>
[`${c.tx},${c.ty}`, c]))`——這份基板疊了多層，同一個基板位置(tx,ty)本來就會出現在陣列裡好幾次(每一層
各自獨立分類一次)，`Map`用同一個key建構時後面的值會直接蓋掉前面的，如果某一層在這個位置判定是
「強制點除」，另一層在同一個位置判定是「正常」而且排在陣列後面，畫面上這一格最終顯示的就只剩下
「正常」——紅框整個消失，即使上面的文字統計(直接逐筆累加，不受這個蓋掉的問題影響)仍然正確算出
「強制點除2」。用Playwright重現：故意讓同一個位置先放FORCE_DELETE、後放OK，畫面確實顯示成沒有紅框
的普通格子；把兩筆順序對調，紅框又出現了——證實問題完全跟資料在陣列裡的先後順序有關，不是隨機的。

已修正：改成先把`grid_cells`依`(tx,ty)`分組(`byPos`，一個位置對應一個陣列，不再是單一Map覆蓋)，畫面
上優先顯示這個位置**所有層裡最需要處理的判定**(強制點除>人工確認>其他)決定要不要畫紅/黃框，hover
文字列出這一格全部層的判定(不只顯示贏的那一個)，方便使用者知道同一個位置到底疊了幾層、各自的結果
是什麼。用Playwright驗證：3層(強制點除/人工確認/正常)疊在同一位置，正確顯示紅框、hover文字列出全部
3個判定；2層(人工確認/正常)疊在另一位置，正確顯示黃框。

教訓：**用`new Map()`從陣列建構「位置→資訊」的查找表時，如果陣列裡同一個key可能重複出現(這裡是疊層
基板，同一個座標本來就會有好幾筆獨立資料)，預設的「後面蓋掉前面」行為很容易在沒有任何錯誤訊息的
情況下悄悄丟資料——而且丟掉的往往是使用者最在意的那種(強制點除)，因為它未必排在陣列最前面。這個bug
之所以拖到現在才發現，是因為之前測試/驗證都用單層基板的案例，同一位置最多只有一筆資料，`Map`覆蓋
的行為根本不會被觸發到——遇到「同一個key理論上可能重複」的資料結構(疊層、多層分析結果都是這種
形狀)，建查找表時要先確認清楚「重複時該怎麼辦」，不能預設用最後一筆蓋掉前面的就好。**

### 再後續：「排除(非目標Wafer)」的位置在BINGO MAP上完全消失，跟真正沒上片的位置分不出來

同一次疊層基板測試，使用者拿真實.strate檔案(Z25709007096，這枚在STRATE補檔那次調查已知混合
FC2643/FCEEB7兩片實體wafer)截圖給Notepad++開啟的原始內容，直接指出DIE_INFO第1、2筆(`sub_pos`是
`0:0`、`0:1`，`bin=1`，確實有真實資料)，但BINGO MAP畫面上這兩個位置卻是空白：「為什麼0:0，0:1有die
但是bingomap是顯示空白」。

查出原因：`webapp/app.py`的`grid_cells_out`只從`result.rows`(通過wafer_ring篩選、真正被分析的die)
建構，`result.excluded`(wafer_ring跟目前輸入的Wafer ID不符、被排除的die——這次的0:0/0:1剛好都是
wafer_ring=FC2643，使用者這次填的目標是FCEEB7)完全沒有對應的grid_cells資料。畫面上「這個位置真的
沒有上片」跟「這個位置有die、只是屬於別的wafer被排除」兩種情況，呈現出來的空白格子一模一樣，使用者
沒辦法從畫面上分辨。

已修正：後端新增`excluded_grid_cells`(從`result.excluded`直接用`parse_xy(die.sub_pos)`算出位置，
沿用跟`grid_cells_out`同一種座標語意——都是原始`sub_pos`，不經過`output_position()`轉換，保持
一致)，連同每個位置實際的`wafer_ring`一起回傳；前端`renderSubstrateGrid()`把這些位置畫成灰底斜紋
(跟T點標記、參考基板同一套視覺語言，代表「有東西、但不能選/不屬於這次」)，滑鼠移過去直接告訴使用者
這個位置的die實際上屬於哪個wafer_ring。同一個位置如果**有些層被分析、有些層被排除**(疊層基板的常見
情況)，優先顯示分析結果的紅/黃/藍框，hover文字裡把被排除層的wafer_ring也一併列出，不會只顯示其中
一種而讓另一種資訊完全消失。用真實的Z25709007096檔案+`FCEEB7`當目標Wafer ID驗證過：`0:0`正確顯示
灰底斜紋、hover文字正確顯示「此位置有die，但屬於wafer_ring=FC2643」。

教訓：**跟前一則(疊層時同一位置的判定被Map覆蓋)是同一個根源的變體——「這個位置沒有畫面資料」在
BINGO MAP格子圖上永遠只有一種呈現方式(空白)，但背後可能對應好幾種完全不同的原因(真的沒上片／
屬於別的wafer被排除／同一位置的其他層蓋掉了這一層)，使用者只能看到「空白」這個表象，猜不出背後
的原因是哪一種。這次(還有排除49顆的wafer_ring提示那次)的共同解法都是同一個方向：**畫面上每一種
「看起來一樣」的狀態，只要背後的成因不同，就要有辦法讓使用者不用開檔案，直接從畫面(顏色、樣式、
hover文字)分辨出來是哪一種**——這是這整個專案在「誤吸偏移／BIN點除」這個功能上，這幾天連續三次
被使用者拿真實資料抓到的同一類疏漏，值得往後新增任何BINGO MAP相關功能時都先想一遍：這個空白/這個
顏色，有沒有可能背後其實有好幾種不同成因混在一起看不出來。**

教訓：**又一次「決定『這裡刻意不動』時，範圍畫得不夠大」——這次連前一次(見上面「die_map key順序」
那則)自己親手寫的顧慮都不夠：知道要保護「T點公式」不被連帶弄壞，卻沒想到公式的兩個輸出跟下游座標系
的對應關係，也是這條保護鏈的一部分。「這個東西本身沒有被修改」不等於「這個東西的意義沒有被連帶
影響」——只要它依賴的其他東西變了，就算它自己一個字都沒改，也可能已經是錯的，只是還沒有人踩到而已。
擱置的已知風險最怕的就是「看起來平安無事」，因為那不代表沒問題，只代表還沒被用到會暴露問題的那個

## ①補資料頁：基板形狀不是完整矩形時，「本來就不存在的位置」跟「還沒填的位置」畫面上長得一樣

使用者拿一枚已載入的真實範本回報：「為什麼這顆24:6沒有反黃確無法帶入座標會跳過去」——這一格既不是
藍色(已對應wafer座標)，也不是黃色(手動標記不上片)，滑鼠點了也填不進座標，就是很單純的空白格。

查程式碼發現這其實是已知、已經在別的地方處理過的行為：`renderSubstrateGridInto()`畫的是
`substrateBounds`(涵蓋整個基板範圍的矩形bounding box)，但基板本身的形狀不一定是完整矩形——
`skipRectangleBetween()`(拖曳批次標記不上片)早就有這個防呆，註解直接寫「skipping cells that fall
outside the actual substrate shape...those must never end up counted in skippedPositions.size」，
但這個防呆只做在「拖曳批次標記」這一條路徑，畫面渲染(`renderSubstrateGridInto()`)跟「單點點擊標記
不上片」(`handleSubstrateCellClick()`)兩處都沒有對應處理：畫面上「這格不存在」跟「這格還沒填」用的
是同一種樣式(純白/預設底色)，肉眼完全分不出來；單點點擊如果不小心點到這種格子，`skippedPositions`

已修正：`renderSubstrateGridInto()`新增`validPositions`(`substratePositions`的Set)，畫面範圍內但不在

說明「基板範本裡本來就沒有這個位置」；`handleSubstrateCellClick()`的標記不上片分支也補上跟
`skipRectangleBetween()`一致的防呆，點這種格子不會有任何效果。用真實範本(`2070_V27NVJH_
Z281226C_20260812221959.strate`，理論80格、實際75格、5格本來就不存在)驗證：這5格正確顯示灰底斜紋，
在skip模式下點擊也正確被忽略。

教訓：**這是這幾天在「哪些畫面狀態看起來一樣、背後成因卻不同」這個主題上第三次踩到的變體(前兩次是
疊層基板同一位置的判定被覆蓋、排除的wafer_ring位置顯示空白)——這次還多了一層：**防呆邏輯本身已經
存在(`skipRectangleBetween()`早就處理過)，但只覆蓋了一條互動路徑，沒有推廣到其他會摸到同一份資料
的路徑(畫面渲染、單點點擊)**。發現一個「這個狀態需要特殊處理」的規則時，值得順手檢查一下同一份
底層資料還有哪些別的進入點(渲染、單點擊、拖曳、批次API)，不能只在第一個踩到問題的地方補洞，讓
同一個漏洞在其他路徑上繼續開著。**

## ②誤吸偏移頁：結果表沒有原始wafer座標欄位，逼使用者拿旋轉過的預覽圖座標來對表

使用者回報一個具體mis-pick案例：「T點x往右偏1，應該會在第15顆吃錯bin7，原本座標是8:48那顆是bin1，
吃錯那顆應該是bin7 9:48」，附了wafer預覽圖上滑鼠停留的座標截圖。實際去查`_classify_row()`(DB機型
是`nominal_xy=(fx,fy)`直接identity，`_apply_offset()`對DB也是`(fx+dx,fy+dy)`直接相加，沒有任何額外
轉換)，再用真實FRM資料(`8P065800A1_T3_DA62.frm`)直接算`wafer_map.bin_at()`——這個座標系裡`y`最大只到
45，8:48整個座標的y=48已經超出這片wafer的實際範圍，不可能是後端拿來算偏移用的那組`wafer_xy`原始值。

往回查才發現：使用者拿來讀座標的wafer預覽格(`app.js`的`renderWaferPanel()`、`mispick.js`的
`renderWaferGrid()`)，滑鼠停留顯示的`x:y`是`waferCellsByPanel`/旋轉後的陣列——也就是套用了
`waferAngleByPanel`(0/90/180/270度，使用者截圖裡設的是90°)之後的**顯示座標**，跟STRATE檔案裡
`DIE_INFO`的原始`wafer_xy`欄位(`_classify_row()`真正拿去算偏移的那組數字)不是同一個座標系，兩者只有
在角度=0°時才會重合。而更根本的問題是：`/api/mispick/analyze`回傳給前端結果表(`action_rows`)的欄位
只有`tx`/`ty`(基板位置)跟`actual_bin`(偏移後的BIN)，完全沒有暴露`fx`/`fy`(原始wafer座標)或
`nominal_bin`(偏移前的BIN)——這兩個欄位其實`MispickRow`裡老早就算好了(`row.fx`/`row.fy`/
`row.nominal_bin`)，只是沒有接到`action_rows_out`跟畫面表格上。使用者除了自己開CSV(有這幾欄)以外，
沒有任何方式在畫面上直接核對「這顆的原始wafer座標、原本BIN是什麼」，只能被迫去看視覺預覽圖，而
預覽圖的座標系又跟角度設定綁在一起——這就是這次「兜不起來」的真正成因，不是偏移計算本身算錯。

已修正：`app.py`的`action_rows_out`補上`fx`/`fy`/`nominal_bin`三個欄位(跟CSV已有的欄位同名)，
`mispick.js`結果表新增「原始Wafer座標」「原本BIN」兩欄，直接列在「TX:TY」「實際BIN」旁邊——之後
要核對任何一顆的偏移計算，直接看這張表就有完整的「原始座標→原本BIN→偏移後BIN」全部資訊，不用再
去猜預覽圖當下是幾度角、有沒有勾鏡像。

教訓：**這次沒有找到計算邏輯本身的錯誤，但找到了一個「讓使用者被迫用錯誤方法自行核對」的介面缺口
——後端明明已經算出使用者真正需要的資料(`fx`/`fy`/`nominal_bin`)，卻沒有把它端上畫面，逼使用者去
用另一個目的不同、座標系也不同的畫面(帶旋轉設定的wafer預覽圖)土法煉鋼，才會產生看似「算錯了」的
假警報。跟這幾天處理過的其他案例合起來看：只要工具沒有主動把「使用者驗證這個判定所需的完整資訊」
放在同一個畫面上，使用者就會被迫去拼湊來自不同座標系、不同用途的畫面線索，而這種拼湊本身就是誤判
的來源——不是使用者的錯，是工具沒把驗證路徑做完整。**

## ②誤吸偏移頁：BINGO MAP的紅/黃框疊回wafer圖上對應的原始座標，不用再肉眼對照

上一則的修正(結果表新增fx/fy/原本BIN欄位)只解決了「文字」層面的核對，使用者接著提出更直接的要求：
「我要改良誤吸這個頁面的bingomap的紅框要在正常的wafer圖檔對應哪一顆，像①補資料頁的批次選取預覽圖
那樣，我才可以知道那顆bingomap紅框跟wafer圖的那一顆是被誤吸」——也就是不只給座標數字，而是直接在
wafer圖上把每一顆強制點除/人工確認的位置標出來，跟BINGO MAP結果表用同一個編號對照。

實作重點是座標轉換必須跟`rotateWaferArray()`(wafer預覽圖旋轉/鏡像用的那套公式)完全一致，否則就是
再犯一次這幾天處理過的同一類錯誤(T點公式配對錯欄位、BINGO MAP欄位排序沒跟著wafer圖修正)——這次
先把公式抽成一個純函式`rotateWaferPoint(x, y, rawBounds, angleDeg, mirror)`，`rotateWaferArray()`
改成呼叫它處理陣列中每一顆，標記疊圖`renderWaferGrid()`裡也呼叫同一個函式把`action_rows`的原始
`fx`/`fy`轉成當下角度/鏡像設定下的顯示座標，兩處保證用同一條公式，不會像T點那次一樣事後才發現
兩處各自維護、悄悄分岔。用真實情境驗證(Playwright)：angle=0時標記落在原始座標(1,2)；切到
angle=90後，標記正確跟著整片bin色塊一起轉到(2,3)(用手算`rotateWaferPoint()`公式驗證吻合)，沒有
停在舊的screen位置——確認轉向設定改變時，標記不會脫離對應的bin色塊。

另外確認了一個關鍵的座標語意：wafer圖左邊(原始/未套用偏移)、右邊(套用目前機台偏移量)兩張圖用的是
「同一組screen(x,y)代表同一個原始wafer座標」——右圖只是同一格顯示的bin顏色換成套用偏移後查表的
結果，screen座標本身沒有變。所以每一顆action_rows的標記直接疊在兩張圖「同一個」screen(x,y)即可，
不需要為右圖另外算一次位移過的座標——這一點如果算錯，會在角度=0、偏移量≠0時最容易被踩到(兩張圖的
標記位置對不齊)，值得特別留意。

已新增：`/api/mispick/analyze`的`action_rows`補上`actual_map_x`/`actual_map_y`(偏移後實際位置，
`row.actual_map_xy`早就算好，只是沒有傳出來)；`mispick.js`的`renderWaferGrid()`用`fx`/`fy`+
`rotateWaferPoint()`算出每一顆的顯示座標，疊在兩張wafer圖上(紅框=強制點除、黃框=人工確認，格子裡
顯示對應結果表的「No.」編號，滑鼠移過去顯示完整判定文字)，圖例新增一項說明。技術細節見
`webapp/README.md`。

## ①補資料頁：wafer圖拖曳矩形批次選取，選出來的順序不管往哪個方向拖都固定不變

使用者截圖附了兩張圖：wafer圖上拖出一個矩形選取，跟真實`.strate`檔案(Notepad++開的DIE_INFO段)並排
比對，回報「當我直接拉選要讓順序幫我自動遞增或者遞減，我發現我拉完順序都會亂跑」。真實檔案裡同一列
(Y都是48)的`wafer_xy`是由大到小排列(23,22,21,...,9)，使用者拖曳選取出來的順序也剛好是23到9，兩者
一致；問題出在使用者的預期——「往哪個方向拖，應該決定是遞增還是遞減」——跟工具實際行為對不上。

查`scanRectangle(x1, x2, y1, y2, panelIndex)`(`app.js`，拖曳矩形批次選取bin1格子的實作)：
```js
const xLo = Math.min(x1, x2), xHi = Math.max(x1, x2);
const yLo = Math.min(y1, y2), yHi = Math.max(y1, y2);
for (let x = xLo; x <= xHi; x++) { for (let y = yLo; y <= yHi; y++) { ... } }
```
呼叫端`scanRectangle(localDragStart.x, end.x, localDragStart.y, end.y, panelIndex)`明明把「拖曳起點→
終點」的先後順序(也就是使用者實際拖曳的方向)完整傳進來了，但函式內部第一步就用`Math.min`/`Math.max`
把範圍重新排序成「X由小到大、Y由小到大」——drag方向這個資訊在這裡被直接丟棄，不管使用者從左往右拖
還是從右往左拖，選出來的順序永遠是同一種(由小到大)。這不是「順序亂跑」(順序其實是固定的)，而是
「順序固定但使用者以為拖曳方向會決定順序」，兩者的落差造成使用者觀察到的「亂跑」現象——這次剛好因為
使用者是由大到小拖(23→9)，跟固定的由小到大順序不一致，才被發現。

已修正：拿掉`Math.min`/`Math.max`重新排序，直接沿用drag起點→終點的實際方向逐格前進(`x1→x2`，
`y1→y2`)——往右拖(或往下拖)選出來就是遞增，往左拖(或往上拖)就是遞減，跟使用者實際拖曳的方向一致。
用Playwright驗證：同一組座標範圍，從大到小拖給出遞減順序、從小到大拖給出遞增順序，兩個方向都跟
拖曳方向吻合。這個函式沒有pytest涵蓋(純前端互動邏輯)，用真實情境的Playwright腳本模擬mousedown/
mouseup事件驗證。

教訓：**這是「函式明明拿到了完整的資訊(起點、終點、兩者的先後順序)，卻在函式一開始就把其中一部分
資訊丟棄」的典型案例——`Math.min`/`Math.max`看起來像是常見、安全的「正規化範圍」寫法，但正規化的
同時也把「方向」這個語意抹掉了，而這裡「方向」剛好是使用者真正在意、真正想控制的那個維度。寫排序/
正規化邏輯時，值得多想一步：這個正規化動作是不是順手丟掉了呼叫端原本刻意保留、之後會需要的資訊。**

## ①補資料頁：wafer角度≠0時，範本/參考基板的座標跟畫面對不齊——連產生出來的.strate檔案都可能是錯的

使用者比對①②兩頁「同一片wafer、同一份.strate、同樣角度90°、無鏡像、同樣T點座標」跑出來的圖，發現
①頁的座標分佈跑到wafer下方、②頁卻跑到wafer左邊，懷疑兩頁的座標規則不一樣。先用真實FRM資料交叉驗證
①②兩頁在角度=0/鏡像=off時wafer圖逐格(2576格)完全一致，排除底層資料/公式不同的可能；再追查角度≠0
時①頁本身的行為，才挖出一個範圍遠比使用者原本問題更大的bug。

根源：`renderWaferPanel()`畫格子的迴圈永遠在**當下角度/鏡像轉過的顯示座標**空間裡跑(`xOrder`/`yOrder`
來自`waferBoundsByPanel`，是`rotateWaferCells()`轉過的)，但判斷「這一格是不是已經被選過/來自範本/
被參考基板占用」的三處比對——`picksByLayer[li].some(p=>p.x===x&&p.y===y)`、`isReferencedAt()`、
`isStagedOnPanel()`——用的`picksByLayer`/`referenceSubstrates`裡的座標，只要是從`loadTemplate()`
(讀範本.strate)或`loadReferenceFiles()`(讀參考基板)進來的，全部是**檔案自己記錄的原始wafer_xy**
(`_die_info_to_picks()`直接`wafer_xy.partition(":")`，完全沒有套用旋轉)——角度=0時原始座標剛好等於
顯示座標，兩者看起來一致，一旦轉了角度，「畫格子用顯示座標、判斷用原始座標」這兩個迴圈其實活在兩個
不同的座標系，比對永遠對不上，範本/參考基板讀進來的座標會顯示在完全錯誤的位置。

更嚴重的是：使用者用**滑鼠點擊/拖曳**選取的座標，走的是相反的路——`wireGridDragEvents()`直接把
`dataset.x/y`(當下顯示座標)存進`stagedPicks`/`picksByLayer`，這條路徑在角度=0時沒問題，但角度≠0時
存進去的其實是「轉過的螢幕座標」，不是這片wafer真正的物理座標——而`generateStrate()`把`picksByLayer`
直接(只拿掉`panel`欄位)當成`wafer_xy`送進`/api/generate`寫進檔案。也就是說：**只要在角度≠0時點選/
拖曳過wafer格子，產生出來的.strate檔案裡wafer_xy欄位寫的是螢幕上轉過的座標，不是這片wafer真正的
物理座標**——這是本來要修的「畫面對不齊」問題之外，另一個獨立、更嚴重、會直接寫壞產出檔案的bug，是
在往回查「①頁畫面座標為什麼跟②頁不一樣」的過程中才發現的。

已修正：把`rotateWaferCells()`裡的旋轉公式抽出成單點函式`rotateWaferPoint(x,y,rawBounds,angleDeg,
mirror)`(原始→顯示)，新增其反函式`unrotateWaferPoint(nu,nv,rawBounds,angleDeg,mirror)`(顯示→原始，
逐一角度手推、用真實座標範圍跑960組round-trip驗證無誤)。統一儲存慣例：`picksByLayer`/`stagedPicks`
一律存**原始wafer座標**(範本/參考基板讀進來的本來就是，現在點擊/拖曳存進去之前也先用
`unrotateWaferPoint()`換算回原始座標)；`renderWaferPanel()`的比對迴圈、`wireGridDragEvents()`的
mouseover提示，改成先把畫面座標轉成原始座標再去查`isCommittedOnPanel`/`isStagedOnPanel`/
`isReferencedAt`；`scanRectangle()`收到的座標改成原始座標，bin色查表跟著換成`waferRawCellsByPanel`
(原始cell map)而不是`waferCellsByPanel`(轉過的)。這樣一來，不管座標是使用者點出來的、還是從範本/
參考基板讀進來的，`picksByLayer`裡永遠是同一種(真正的物理wafer座標)——畫面永遠正確對齊，
`generateStrate()`寫進檔案的`wafer_xy`也永遠是真正的物理座標，不受目前顯示角度影響。

用Playwright在角度=90°下驗證：(1)載入的範本，picked格子的顯示座標精確吻合手算的旋轉公式(不管範本是
在讀wafer之前還是之後載入)；(2)點擊某個顯示格子，pick-table顯示的座標是手算的原始座標，不是螢幕
座標；(3)角度=0時的行為完全沒變(維持恆等變換，跟修正前一致)；(4)單點選取/取消選取、拖曳矩形批次
選取、參考基板佔用格阻擋，三者在角度=90°下都正確運作。

教訓：**這次的根源是「同一份狀態(`picksByLayer`)，被兩條不同的資料來源(使用者互動 vs. 讀檔案)用
兩種不同的座標慣例填入，程式本身沒有任何機制強制兩者一致」——角度=0是這個系統長期以來事實上的
「安全區」(兩種慣例剛好重合)，只要沒人踩出這個安全區，問題永遠不會被看見；使用者一旦帶著角度≠0
的設定去讀取範本/參考基板(這正是「角度」這個功能存在的理由——修正wafer的實際擺放方向)，兩種慣例
的落差立刻現形。跟這幾天處理過的其他座標系混淆案例(T點公式配對、BINGO MAP欄列順序)同一個更大的
主題：**一個座標，只要它可能被多個入口(互動、讀檔、產生輸出)分別存取，就必須明確定義並強制統一
它「活在哪個座標系」，不能讓某個入口自己選一種方便的慣例，指望角度剛好等於0的巧合幫忙掩蓋分歧。**

## ①補資料頁：「依序輪流分配到全部層」分好幾批操作時，越前面的層越容易多分到——每批都從第1層重新算起

上一則剛上線的「依序輪流分配到全部N層」功能，使用者實際用起來(4層，框選好幾批分開按這顆按鈕)回報：
「沒有先填進去第四層就跑到第一層」——四層最後的顆數是13/13/12/11，不是平均循環該有的樣子(49顆/4層
理論上該是13/12/12/12，只有一層比其他層多1顆)。

查出原因：`commitStagedPicksRoundRobin()`原本是`stagedPicks.forEach((pick,i) => picksByLayer[i % n]
.push(pick))`——每一次呼叫都是獨立的一批，`i`永遠從0算起，也就是「這一批的第1顆」永遠分到第1層。
如果分好幾批操作(這正是這個功能設計上預期的用法——框一批、按一次、再框下一批)，且每批顆數不是N的
倍數，每一批多出來的餘數都會往前面幾層(尤其第1層)偏，批數越多，偏移就越明顯累加——這正是使用者
看到的「都跑到第一層」。用同樣的4批分法(顆數5,7,6,4)手算重現：舊邏輯得到`[7,6,5,4]`(第1層比第4層
多3顆)，理論上應該平均循環的正確結果是`[6,6,5,5]`(差距最多1顆)。

已修正：新增`roundRobinCursor`記住上一次輪流分配「轉到第幾層」，`commitStagedPicksRoundRobin()`改成
用`(roundRobinCursor + i) % n`接著上次的位置繼續轉，不再每批都從第1層重新起跳；呼叫結束後把游標往前
推進這批的顆數(`roundRobinCursor = (roundRobinCursor + count) % n`)。只有整個層狀態被重設時
(`resetLayerState()`——換層數、清空選取、換範本/骨架...)才會把游標歸零，因為那些情況下每一層的內容
本來就整個被清空重來，游標接著算沒有意義。同時把這個游標一併存進`localStorage`(`saveState()`/
