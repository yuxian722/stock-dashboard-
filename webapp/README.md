# BINGO MAP 補資料工具 — 網頁雛形

包著`bingomap` core的一個最小網頁介面，流程對應原始需求：開網頁 → 輸入資訊 → 產生空白骨架 →
點選/框選wafer座標 → 下載`.strate`。所有業務邏輯都留在`bingomap`裡，這裡只是HTTP+前端。

wafer bin資料（綠/粉紅那張圖）**已經可以自動讀取**：輸入LotNo+Barcode ID，`/api/frm`會用
`frm_reader.py`直接讀真實FRM二進位檔案（`{FRM_PATH}\{LotNo}\{barcode前2碼}\{barcode第3~6碼}`），
只有這個Flask process本身跑在連得到`F:\SMAP\FRM\`網路磁碟機的電腦上才會成功。連不到的話還是可以
用「貼上`x,y,bin`文字」手動輸入當備援，兩種方式最後都是同一份`waferCells`，後面流程完全一樣。

wafer圖的座標軸方向刻意對齊真正的`WaferCoordinate.exe`：X軸是**右到左遞增**，原點(0:0)在
**右上角**，不是左上角(使用者提供了實機截圖比對確認)。點選/拖曳/反查等邏輯都是照儲存在
`dataset.x`/`dataset.y`的真實座標值運作，只有畫面顯示順序被鏡像，不影響任何座標計算或
產出的`.strate`內容。

## 執行

**Windows雙擊執行**：直接雙擊 `webapp/launch_bingomap.bat`，第一次執行會自動裝套件，
之後每次雙擊就直接啟動（仿照`da_bot/launch_da_bot.bat`的做法）。

**手動執行**：
```
pip install -r webapp/requirements.txt
cd stock-dashboard-   # repo根目錄
python3 -m flask --app webapp.app run --port 5000
```

開瀏覽器到 `http://127.0.0.1:5000/`。

## 操作方式

1. 填基本資訊，按「產生空白骨架」
2. **Wafer Bin資料**：填LotNo+Barcode ID按「自動讀取FRM檔案」（能連F槽時）；連不到就改貼`x,y,bin`文字按「載入Wafer地圖(文字)」
3. 在網格上**點一下**加選單一顆，或**拖曳出一個矩形**自動依序選取範圍內所有綠色(bin1)的格子（跳過其他顏色跟已選過的），下方會即時顯示對應到基板的哪個位置
4. 已選數量會即時跟目標數量比對，不符合時是紅字
5. 數量對了之後按「產生檔案」，會直接下載`.strate`；數量不符會跳出跟WaferCoordinate.exe同樣文字的錯誤訊息

wafer圖跟基板圖（bingomap）刻意用同一套格子大小、座標軸標籤樣式，方便肉眼對照兩張圖的位置；滑鼠移到
任一格上，格子上方會即時顯示目前座標。基板圖上方有「標記『不上片』模式」按鈕：開啟後點基板格子＝標記/
取消該格「不上片」（顯示黃色），**拖曳一個矩形＝整批標記範圍內所有格子不上片**（只會標記真正屬於這個
基板規格的格子，不會誤把矩形範圍內、但實際不存在的格子也算進去而拉低目標數量）；不上片的位置不會被
wafer座標填入，目標數量也會自動扣除對應格數（`/api/generate`的`skip_positions`欄位；未上片的基板位置
本來就整筆省略不寫進`DIE_INFO`，不上片只是提前把它從「可填入」清單拿掉，不需要改bingomap core）。切換
回關閉時，點基板格子恢復成原本的wafer座標反查功能。

**實際要上片的數量**（2026/08/18新增）：批次結尾常常上不滿理論總數（例如理論307顆，這批實際只會上
100顆），這種情況不用手動一格一格拖曳標記結尾的格子——在「已選座標」區填入實際要上片的數量、按
「套用」，會自動把**基板填入順序的前N格維持可上片，後面的格子整批標記「不上片」**。這個動作每次都是
重新計算（取代之前的不上片標記，不是疊加），按鈕旁邊會顯示套用結果（維持幾格可上片、標記了幾格不上
片，或是設定的數量≥理論總數所以沒有格子被標記）。套用之後仍然可以用手動標記/拖曳矩形調整個別格子
（例如結尾100顆裡剛好有幾顆已知是壞的，可以另外再標記）。

## 複製既有.strate為範本

畫面最上方有「複製既有 .strate 為範本（選用）」區塊，可以選擇一個舊的`.strate`檔案(或直接貼上內容)，
載入後會自動把「基本資訊」跟「已選座標」都帶入——不用重新輸入批號/基板規格，也不用重新點一次wafer座標。
基板位置的順序是**照範本檔案原本記錄的順序**，不會重新用DB/ESEC規則產生，所以不會有「機型抄錯導致順序
跑掉」的風險(這正是CLAUDE.md記錄的那個真實案例的規則)。載入後可以直接改基板流水號(`SUBSTRATE_ID`)或
時間就產生新檔案，或是繼續在wafer圖/基板圖上調整座標。如果之後又點了「產生空白骨架」，就會改回用
DB/ESEC規則重新產生順序，等於放棄範本模式。

（修過的bug：貼上內容或選檔案後點「載入範本」，曾經會出現「檔案格式解析失敗：Missing
[DIE_INFO_BEG] marker」，即使檔案本身完全正常。原因是瀏覽器的`<textarea>`讀回`.value`時會把
CRLF自動正規化成純LF(這是HTML規格行為，不是bug)，而`StrateFile.parse()`原本寫死只接受CRLF，
碰到被正規化過的內容就直接判定成格式錯誤。已經修成`parse()`同時接受CRLF跟純LF(內部先正規化
再切割)，輸出的部分完全沒動——`to_text()`還是永遠寫CRLF，不影響機台讀取。）

## 疊層(一次上多顆，支援到8層以上)

2026/08/17：使用者提供了一份真實的**8層**`.strate`範例(`bingomap/tests/fixtures/
2070_V25NVDY_F2006908_20260702203138.strate`)，才發現原本以為「每多一層就要多一段
`DIE_INFO_OTHER_LAYERn`」的猜測是錯的——真實格式其實簡單很多：**`[DIE_INFO_BEG]`永遠只放
「目前這一層」(f9最大的那層)，其餘所有層全部混在同一段`[DIE_INFO_OTHER_LAYER_BEG]`裡，
靠每一列自己的f9(最後一欄)分辨屬於第幾層**——8層的例子裡，DIE_INFO放f9=8(7筆)，
OTHER_LAYER放f9=1~7(各7筆、共49筆)，照f9由小到大分組排列。這個發現讓`bingomap/strate.py`
完全不用改(它本來就是逐列讀f9、沒有假設同一段內f9是常數)，只要在`assignment.py`加一個
`assign_layers()`把N層通用地組出這個結構即可。

基本資訊區勾選「疊層(一次上多顆)」後，會多出「疊幾層」數字輸入框(預設2，最多16)。每層的f9
**自動編號1~N**(第N層＝目前層，寫進`DIE_INFO`；其餘層依f9由小到大寫進`DIE_INFO_OTHER_LAYER`)，
不用手動填f9。選座標區改成**同時顯示N張BINGO MAP**(各自獨立的格子圖、hover座標顯示、已選
清單)，用flex排版自動換行，不管幾層都排得下。

### wafer片數(1或2)跟疊幾層(N)是兩件獨立的事——2026/08/18修正

第一版把「疊N層」跟「N片wafer」寫死1:1綁定(第i層只能用第i片wafer的座標)，使用者實測後指出這是
錯的：**疊幾層(N)完全由物理上的die-attach堆疊決定，跟座標來自幾片wafer無關**——不管疊2層還是
8層，座標可能全部來自同一片wafer，也可能來自兩片不同的wafer，但「這是第幾層」永遠不該取決於
「這是第幾片wafer」。

修正後的操作方式改成**「先選wafer座標→點進哪一層的BINGO MAP才寫入哪一層」**兩步驟：

1. 在wafer圖上點一格＝**選取(待寫入)**該座標(橘色虛線框)，還沒有指定要進哪一層；拖曳一個矩形＝
   一次選取一整批(整批一起待寫入)。再點一次已選取的格子可以取消選取。
2. 選好之後，點下方**任一層**的BINGO MAP(格子區域)，就會把目前所有「待寫入」的座標整批寫入
   點的那一層，跟座標原本是從哪一片wafer選的沒有關係。已寫入的格子統一用藍色實線框+格內數字
   標示是第幾層(不是每層配一種顏色，N到8層以上顏色會分不清楚)。
   - 如果目前沒有任何待寫入的座標，點BINGO MAP格子會退回原本的「反查」功能：查這格對應到哪個
     wafer座標(在wafer圖上用橘色實線框標示)。
   - 「標記『不上片』模式」開啟時，點BINGO MAP格子永遠是標記/取消不上片，優先權比待寫入寫入
     還高。

這個設計直接解決了使用者最早反映的「切換層很容易點錯」問題——目標層不是靠一個容易忘記切換的
按鈕決定，而是**點下去的當下**才決定要寫入哪一層，寫錯層的機會小很多。

**跨兩片wafer**：勾選「跨兩片wafer」後固定多出**一個**額外的wafer讀取區塊(FRM或貼文字都獨立
一份)，畫面同時顯示兩張wafer圖，兩張圖都可以直接選取待寫入的座標，選完點哪一層的BINGO MAP
就寫入哪一層——**跟疊了幾層完全無關，固定就是2片**(不會因為疊8層就變成8片wafer)。已經在某一
片wafer上寫入過的座標，全域(不論哪一層)不能在**同一片**wafer上重複選取；但兩片wafer之間即使
座標數值相同也不算重複，因為是不同的實體wafer。

**「跨兩片wafer」不需要先勾選「疊層」**(2026/08/18修正)——第一版把這個勾選框藏在「疊層」
底下，沒勾疊層就看不到、也用不了，但使用者指出跨兩片wafer的需求在**只有第1層(完全沒有疊層)**
時一樣會發生(例如第一片wafer好的顆數不夠填滿，要換第二片wafer繼續選)。現在這個勾選框永遠
可見、可以獨立勾選，跟「疊層(一次上多顆)」勾選框互不影響——沒疊層時勾了會多出第二張wafer圖，
兩張圖選的座標最後都寫入唯一的那張BINGO MAP；疊層時則跟前面說明的一樣，寫入哪一層由點哪個
BINGO MAP決定。

**注意**：更改「疊幾層」數字或切換「跨兩片wafer」勾選框，都會**清空目前已選的座標跟wafer
資料**，重新產生對應設定的畫面結構——這是刻意的簡化設計，沒有嘗試把舊設定的資料重新對應到
新設定，避免猜錯映射關係。建議先確定好要疊幾層、要不要跨兩片wafer，再開始選座標。

（修過的bug：先勾「跨兩片wafer」、再載入.strate範本，第二張wafer圖會無聲無息消失——
`loadTemplate()`原本不管使用者當下設定為何，一律把「跨兩片wafer」強制重設成關閉，跟「wafer片數
是使用者獨立設定、不該被其他動作覆蓋」這個原則互相矛盾。已經修好：載入範本不再動「跨兩片wafer」
的狀態，維持使用者原本的設定；不論先勾選再載入範本、還是先載入範本再勾選，都能正常運作。）

wafer圖跟基板圖(bingomap)滑鼠移到格子上時，除了原本上方的文字狀態列，格子正上方也會浮出一個
跟著游標的座標提示框，不用把視線移到畫面上方找狀態列。

（修過的bug：第二個wafer面板的「自動讀取FRM檔案」按鈕原本按下去完全沒反應——`loadFrmInto()`用
樣板字串組狀態文字元素的id時，因為那個id剛好是連字號命名而不是底線命名，組出一個不存在的id，
`getElementById`拿到`null`直接讓函式在第一行就拋例外，連fetch都沒發出去，畫面上什麼提示都不會
顯示。已經修好並用Playwright驗證錯誤訊息會正確顯示紅字、成功載入也會正確渲染出wafer圖；這次
N層重構把每個wafer面板的id都改成統一規則產生，不會再有這種手動組id漏改的風險。）

## T點標示

使用者提供了真實wafer目視檢查畫面的照片，指出畫面下方座標列有一個「T點」欄位，畫面上wafer圖也有一個
用特殊格紋畫出來的固定記號，想要我們的wafer圖也標出來。這個過程來回猜了四次才找到正確答案——過程
記錄下來避免以後又猜錯：

1. 第一次猜：以為T點是「Ref. Point: -19, 1」這個固定值（畫面MAP INFORMATION AREA有顯示）——使用者
   一開始也同意了，但後來比對發現有問題（見下）。
2. 第二次猜：比對兩張照片發現「COL 46 ROW 56」在滑鼠移到不同格子時完全沒變，一度以為那才是固定的
   T點——結果使用者澄清COL/ROW其實只是這片wafer本身的**總欄數×總列數**（layout尺寸），跟座標無關，
   猜錯。
3. 使用者直接說明：「T點就是畫面有特殊格紋記號，滑鼠點進去會顯示T點在下方欄位」——確認T點是wafer圖
   上一個**特定的格子**，用特殊紋路畫出來，不是普通BIN1/BIN7的die。
4. 第三次猜（**錯**）：使用者傳來真實的`.frm`檔案（Lot No 8P964000、Barcode ID K84E13，存成
   `bingomap/tests/fixtures/8P964000_K8_4E13.frm`）。直接解析後發現`bin_kind_count`只有2種
   （BIN1/BIN7），沒有第三種die分類代表T點；檔案裡的`reference_point_x`/`reference_point_y`欄位
   （`frm_reader.py`早就有解析、只是之前沒用到）算出來剛好落在die範圍**之外**的一格，一度以為
   「不是die」這點就足夠確認是T點——**結果使用者傳了一張wafer圖跟目視檢查小視窗並排的照片，直接
   證明這個位置在wafer圖的最外面、明顯在整片wafer之外，錯了**。
5. 第四次猜（**錯**）：使用者接著直接在WaferCoordinate.exe裡把滑鼠點在真正的T點格子上，回報當下
   顯示的X(直/行)=-19、Y(橫/列)=1，同時附上一張很清楚的照片。我把畫面上十字交叉記號的位置誤判成
   wafer正中央附近（讀小圖上的座標軸標籤讀錯），改成T點＝`(columns//2, rows//2)`（幾何中心）——
   **結果使用者又傳了一張新照片，畫面上「Wafer座標：18:0」的位置明顯在wafer最外面，證明幾何中心
   還是不對**。
6. 使用者接著給出決定性的說明：「這是DB格式的圖檔，比照左邊跟右邊可以發現是鏡像180度，所以紋路T點
   會是上方中心線往右第五顆第一排位置」——直接用**我們自己畫面的座標系統**描述正確位置：第一排
   （row 0），從水平中心線往右數第5顆。這個「5」剛好就是這片檔案自己的`reference_point_x`（5）——
   **確認T點＝`(columns//2 - reference_point_x, 0)`**：wafer水平中心往右偏`reference_point_x`格、
   固定在row 0（這個機型的flat/notch邊）。用真實檔案驗證：`46//2 - 5 = 18`，跟使用者回報的
   `(18, 0)`完全吻合。`reference_point_y`目前沒用到（row固定是0，還沒驗證notch在其他邊的wafer是否
   一樣）。

已經照第6點重做：wafer圖上對應的那一格疊加一個深色斜紋紋路標示（跟其他狀態疊加顯示，不會互相蓋
掉），滑鼠移過去會顯示「T點」，因為它不一定是BIN1 die，本來就不能被選取/待寫入。只有透過「自動讀取
FRM檔案」載入才會有這個標示（手動貼`x,y,bin`文字沒有這些header可以算）。FRM讀取成功的狀態文字也會
直接顯示算出來的座標（例如「T點＝18:0」），方便使用者比對——**這次是靠使用者直接用文字描述位置
（不是只靠照片猜），而且用真實檔案驗證公式算出來的座標剛好對上，信心比前幾次高，但`reference_point_y`
未使用這一點還沒驗證過，如果之後發現某片wafer的T點對不上（尤其是notch方向不同的wafer），麻煩直接
回報**。

## 參考同一片wafer的其他基板

同一片實體wafer常常會切成好幾枚基板，各自產生各自的`.strate`。「複製既有.strate為範本」欄位下方
另外有一個「參考同一片wafer的其他基板（選用，可多選）」區塊（`#reference-files`，`<input type=file
multiple>`），可以**一次選多個**已經完成的`.strate`檔案，純粹當「參考」疊在wafer圖上——**不會**被
編輯或合併進正在做的這一枚（跟上面「複製既有.strate為範本」是完全不同的動作：範本是把一份檔案的
座標跟基本資訊整個載進來繼續編輯／重新產生；參考檔案的座標只拿來畫在wafer圖上、擋掉重複選取，
它本身的基本資訊完全不會影響目前正在填的表單）。

行為（2026/08/18跟使用者用AskUserQuestion確認過）：
- 參考檔案佔用過的wafer座標，**直接擋掉不能再被選取**——不管是單點還是拖曳矩形選取都一樣，
  跟「已經寫入某一層」的座標擋法完全相同（`isReferencedAt()`），避免跟其他基板選到同一顆wafer die。
- wafer圖上會**分辨是哪一枚參考檔案**佔用的，不是統一畫成一種「已佔用」標示：每個檔案有自己的
  顏色＋字母代號（A、B、C…，超過26個之後改用R27、R28…），格子背景色＝那個顏色、格子文字＝那個
  字母，滑鼠移過去的提示文字跟浮動tooltip也會顯示是被哪一枚基板（SUBSTRATE_ID）佔用的。旁邊的
  `#reference-legend`會列出每個代號對應到哪個基板ID、佔用幾顆。
- 參考檔案的座標一律套用在**第一片wafer(panel 0)**——參考檔案本身沒有「這是第幾片實體wafer」的
  概念(跟「複製既有.strate為範本」載入的座標一樣，都假設是panel 0)，這也符合「參考同一片wafer的
  其他基板」這個功能本身的前提：本來就是同一片實體wafer才需要互相參考擋重複。
- 參考資料是獨立於「疊幾層」「跨兩片wafer」「載入範本」「產生空白骨架」之外的資料——切換這些設定
  都不會清掉已載入的參考基板列表(用Playwright驗證過)，因為它描述的是wafer本身的既定事實，跟目前
  在編輯哪個設定/哪一層無關。要清掉就按「清除參考基板」按鈕(`#btn-clear-references`)。
- 參考檔案的解析沿用既有的`/api/parse_strate`(逐一呼叫，前端迴圈處理多個檔案)，取每個檔案
  `layer_picks`攤平後的全部座標(涵蓋該檔案自己的所有疊層)當作佔用範圍——沒有新增後端API。

## 多分頁架構

首頁最上方有導覽列（`templates/_nav.html`，各頁共用），目前有四頁：①補資料(`/`，本頁)、②誤吸偏移／
BIN點除(`/mispick`)、③Crack位置回推(`/crack`)、④STRATE補檔 XML合併(`/strate-xml`)。導覽列上也先
列出⑤上片狀態人工確認/修正「尚未開發」的項目，之後每移植一個ESEC參考工具的功能就補一個新頁面+
對應路由，不會把不相關的功能硬塞進同一頁。

## 誤吸偏移／BIN點除（`/mispick`）

移植自使用者提供的ESEC 2100參考工具（STRATE座標偏移點除工具v78）。流程：選機型(DB/ESEC)、填「原始
wafer MAP」的FRM LotNo+Barcode ID（跟補資料頁共用同一份`frm_reader.py`）、上傳一或多份已上片`.strate`
檔案、填要比對的完整Wafer ID、機台偏移方向與數量、Good/強制點除/人工確認的BIN設定，按「分析」後每份
STRATE各自列出強制點除／人工確認的清單(含基板座標、Block、TX:TY、實際BIN)，並可下載全部結果的CSV。

**機型預設DB**——2026/08/17用使用者提供的真實DB案例確認：STRATE的`wafer_xy`就是wafer MAP自己的原始
座標，不需要任何轉換，也不限制NOTCH。選ESEC則套用參考工具的公式（NOTCH鎖定270，其他角度直接拒絕
分析）——那套公式沒有用這個系統的真實資料驗證過，選了會顯示警告。詳見`bingomap/mispick_analysis.py`
docstring跟`bingomap/CLAUDE.md`。

**視覺化＋方向微調（2026/08/18）**：使用者要求「誤吸頁也要能看到實際的wafer圖，並且移動T點方向時
BINGO MAP要即時反紅框」。分析結果現在除了原本的表格，還會畫出：
- **原始wafer MAP的實際格子圖**(綠色bin1/紫色bin7)，跟①補資料頁同一套`.wafer-cell`畫法
- **每份STRATE自己的BINGO MAP格子圖**：已上片位置畫藍色，強制點除的位置疊一圈粗紅框、人工確認的
  疊粗黃框，直接對照哪一顆吃到壞BIN，不用只看表格數座標

「偏移與BIN設定」欄位下方新增四個方向按鈕(↑↓←→)：點一下＝把偏移量朝該方向±1、自動重新呼叫分析
（不用每次都手動按「分析」），BINGO MAP的紅框位置會跟著即時更新。切換到另一個軸(例如原本在調Y、
點了←/→)時偏移量會歸1重新開始，因為`make_offset()`本來就只支援單一軸的偏移(符合機台實際故障模式：
一次只會是某一軸系統性偏移，不會是斜向的)。

## Crack位置回推（`/crack`）

移植自同一個ESEC 2100參考工具的Crack模式。流程：選機型(DB/ESEC)、上傳一或多份`.strate`檔案(建議把
同一個完整Wafer ID相關的STRATE都一起上傳)、按「載入STRATE」，畫面左邊是選定基板的格子圖(點格子＝
標記/取消Crack)，右邊是這個Wafer ID匯總後的局部分布散點圖(相對位置，不是絕對wafer座標)，下方會列出
目前標記的Crack清單並可下載CSV。

跟誤吸偏移／BIN點除頁的差異：**不需要wafer MAP、不套偏移**；**任何NOTCH都接受**(不是只有270)；每個
已上片位置一律當成背景BIN1，這個模式不驗證bin正不正確，只負責回推位置。任何一份STRATE缺NOTCH或
基板規格無效，整個分析會直接失敗（不會只跳過那一份），因為這個功能本來就是要把多份STRATE匯總，
悄悄漏掉一份會讓分布看起來不完整卻沒有警示。機型同樣預設DB(identity，不反轉不旋轉)，ESEC選項套用
參考工具原本的TX反轉+NOTCH旋轉。

沒有搬參考工具原本的雙canvas對照圖PNG匯出，目前用HTML表格版的基板圖+散點圖取代，功能等價但視覺
效果較簡單。

## STRATE補檔 XML合併（`/strate-xml`）

2026/08/18使用者提供了機台真實的SECS/AFC交易紀錄log(BAB14站台)，要求「從這裡抓出strate的資料跟
wafer圖檔的資料」。跟前三頁完全不同的地方：**不需要重新手動點座標**——log裡的`StrateMap`事件本身
就已經完整記錄了每一枚基板實際上片的座標資料，直接轉成`.strate`檔案即可；這頁的角色是「資料救援」，
適合基板檔案已經遺失、但機台的SECS log還留著的情況。

流程：上傳log檔案(UTF-16LE，跟browser原生`file.text()`的解碼方式不合，前端改用`file.arrayBuffer()`
轉base64送到後端，由`bingomap/secs_log.py`的`decode_secs_log()`偵測編碼解碼)、按「解析Log」，畫面
列出：
- **基板資料**(`StrateMap`事件)：每一列可以單獨下載成`.strate`檔案，也有「全部下載(.zip)」一次拿到
  全部
- **Wafer Bin Map資料**(`WaferStart`事件的`BinList`)：「顯示/複製座標文字」展開後是`x,y,bin`格式的
  文字，跟「①補資料」頁面「手動貼上wafer bin資料」欄位格式完全一樣，可以直接複製貼過去繼續用；每片
  wafer**同時畫出實際的wafer圖**(綠色bin1/紫色bin7的格子圖，跟「①補資料」頁面wafer圖同一套CSS)，
  並且用不同顏色＋字母把「這片wafer的哪些位置被log裡哪一枚基板(StrateMap)撿走」直接疊在圖上、下面附
  圖例——這是使用者2026/08/18的後續要求「這裡面的wafer mapping資料也幫我跑出一個wafer圖檔讓我知道
  對應你一枚strate」，用`wafer_ring`(基板自己記的來源wafer)對上`frame_id`(wafer bin map自己的wafer
  代號)配對，同一片wafer可能對應好幾枚基板，全部一起疊色顯示；沒有顏色標記的格子代表這份log裡沒有
  找到對應的基板資料(不代表那個位置沒被用過，只是這份log沒記錄到)

**注意：**轉出來的`.strate`檔案`ASSY_LOT`、`OPER`、`MAPPING_LOT`三欄會是空白——這份log完全沒有
記錄這幾項資料(不是我們沒解析，是機台log本身就沒有)，頁面上跟README都有提醒，請下載後自行人工
補上，使用者已經確認這個處理方式可以接受。

技術細節、真實資料交叉驗證過程(尤其是`BinList`座標方向怎麼驗證出來的)見`bingomap/README.md`跟
`bingomap/secs_log.py`模組docstring。
