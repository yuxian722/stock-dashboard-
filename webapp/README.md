# BINGO MAP 補資料工具 — 網頁雛形

包著`bingomap` core的一個最小網頁介面，流程對應原始需求：開網頁 → 輸入資訊 → 產生空白骨架 →
點選/框選wafer座標 → 下載`.strate`。所有業務邏輯都留在`bingomap`裡，這裡只是HTTP+前端。

wafer bin資料（綠/粉紅那張圖）**已經可以自動讀取**：輸入LotNo+Barcode ID，`/api/frm`會用
`frm_reader.py`直接讀真實FRM二進位檔案（`{FRM_PATH}\{LotNo}\{barcode前2碼}\{barcode第3~6碼}`），
只有這個Flask process本身跑在連得到`F:\SMAP\FRM\`網路磁碟機的電腦上才會成功。連不到的話還是可以
用「貼上`x,y,bin`文字」手動輸入當備援，兩種方式最後都是同一份`waferCells`，後面流程完全一樣。

wafer圖的座標軸方向刻意對齊真正的`WaferCoordinate.exe`：X軸是**右到左遞增**，原點(0:0)在
**右上角**，不是左上角(使用者提供了實機截圖比對確認)。點選/拖曳/反查等邏輯都是照儲存在
`dataset.x`/`dataset.y`的真實座標值運作，只有畫面顯示順序被鏡像，不影響任何座標計算或
產出的`.strate`內容。

## 執行

**Windows雙擊執行**：直接雙擊 `webapp/launch_bingomap.bat`，第一次執行會自動裝套件，
之後每次雙擊就直接啟動（仿照`da_bot/launch_da_bot.bat`的做法）。

**手動執行**：
```
pip install -r webapp/requirements.txt
cd stock-dashboard-   # repo根目錄
python3 -m flask --app webapp.app run --port 5000
```

開瀏覽器到 `http://127.0.0.1:5000/`。

## 操作方式

1. 填基本資訊，按「產生空白骨架」
2. **Wafer Bin資料**：填LotNo+Barcode ID按「自動讀取FRM檔案」（能連F槽時）；連不到就改貼`x,y,bin`文字按「載入Wafer地圖(文字)」
3. 在網格上**點一下**加選單一顆，或**拖曳出一個矩形**自動依序選取範圍內所有綠色(bin1)的格子（跳過其他顏色跟已選過的），下方會即時顯示對應到基板的哪個位置
4. 已選數量會即時跟目標數量比對，不符合時是紅字
5. 數量對了之後按「產生檔案」，會直接下載`.strate`；數量不符會跳出跟WaferCoordinate.exe同樣文字的錯誤訊息

wafer圖跟基板圖（bingomap）刻意用同一套格子大小、座標軸標籤樣式，方便肉眼對照兩張圖的位置；滑鼠移到
任一格上，格子上方會即時顯示目前座標。基板圖上方有「標記『不上片』模式」按鈕：開啟後點基板格子＝標記/
取消該格「不上片」（顯示黃色），**拖曳一個矩形＝整批標記範圍內所有格子不上片**（只會標記真正屬於這個
基板規格的格子，不會誤把矩形範圍內、但實際不存在的格子也算進去而拉低目標數量）；不上片的位置不會被
wafer座標填入，目標數量也會自動扣除對應格數（`/api/generate`的`skip_positions`欄位；未上片的基板位置
本來就整筆省略不寫進`DIE_INFO`，不上片只是提前把它從「可填入」清單拿掉，不需要改bingomap core）。切換
回關閉時，點基板格子恢復成原本的wafer座標反查功能。

**實際要上片的數量**（2026/08/18新增）：批次結尾常常上不滿理論總數（例如理論307顆，這批實際只會上
100顆），這種情況不用手動一格一格拖曳標記結尾的格子——在「已選座標」區填入實際要上片的數量、按
「套用」，會自動把**基板填入順序的前N格維持可上片，後面的格子整批標記「不上片」**。這個動作每次都是
重新計算（取代之前的不上片標記，不是疊加），按鈕旁邊會顯示套用結果（維持幾格可上片、標記了幾格不上
片，或是設定的數量≥理論總數所以沒有格子被標記）。套用之後仍然可以用手動標記/拖曳矩形調整個別格子
（例如結尾100顆裡剛好有幾顆已知是壞的，可以另外再標記）。

## 複製既有.strate為範本

畫面最上方有「複製既有 .strate 為範本（選用）」區塊，可以選擇一個舊的`.strate`檔案(或直接貼上內容)，
載入後會自動把「基本資訊」跟「已選座標」都帶入——不用重新輸入批號/基板規格，也不用重新點一次wafer座標。
基板位置的順序是**照範本檔案原本記錄的順序**，不會重新用DB/ESEC規則產生，所以不會有「機型抄錯導致順序
跑掉」的風險(這正是CLAUDE.md記錄的那個真實案例的規則)。載入後可以直接改基板流水號(`SUBSTRATE_ID`)或
時間就產生新檔案，或是繼續在wafer圖/基板圖上調整座標。如果之後又點了「產生空白骨架」，就會改回用
DB/ESEC規則重新產生順序，等於放棄範本模式。

（修過的bug：貼上內容或選檔案後點「載入範本」，曾經會出現「檔案格式解析失敗：Missing
[DIE_INFO_BEG] marker」，即使檔案本身完全正常。原因是瀏覽器的`<textarea>`讀回`.value`時會把
CRLF自動正規化成純LF(這是HTML規格行為，不是bug)，而`StrateFile.parse()`原本寫死只接受CRLF，
碰到被正規化過的內容就直接判定成格式錯誤。已經修成`parse()`同時接受CRLF跟純LF(內部先正規化
再切割)，輸出的部分完全沒動——`to_text()`還是永遠寫CRLF，不影響機台讀取。）

### 後續更正(2026/08/27)：範本可能橫跨兩片物理wafer，載入時要照每顆die自己的wafer_ring分配面板

使用者回報：Z25709007096這份`.strate`載入範本後，畫面上顯示這枚基板「有兩片wafer id FCEEB7/FC2643」，
應該要出現兩片wafer的圖跟分布位置，但只出現一片。

追出原因：`.strate`的`DIE_INFO`/`DIE_INFO_OTHER_LAYER`每一列本來就各自記錄`wafer_ring`欄位(9欄CSV的
第2欄)，這不是整份基板共用一個值，是逐顆die各自記錄——但`loadTemplate()`原本無條件把每一顆讀進來的
pick都指派成panel 0，理由寫的是「a .strate file carries no notion of which physical wafer panel a
die came from」，這個假設本身是錯的。用真實檔案實際統計才發現問題比想像中更細：這枚基板的224顆die
(56顆DIE_INFO+168顆DIE_INFO_OTHER_LAYER)**同一層(同一個f9)裡面就同時混著FC2643(每層12~13顆)跟
FCEEB7(每層43~44顆)兩片物理wafer**，不是「第1層算一片wafer、第2層算另一片」這種乾淨的切法，所以修
的時候不能用「整層對應一片wafer」的簡化，得逐顆die照它自己的wafer_ring分配。

已修正：
- `webapp/app.py`的`_die_info_to_picks()`把每顆die自己的`wafer_ring`一起回傳(不再只在
  `_substrate_summary()`那層取整份基板第一顆的值)
- `app.js`的`loadTemplate()`：先掃過所有pick蒐集出現過的wafer_ring(照第一次出現的順序)——剛好兩種的
  話自動勾選「跨兩片wafer」、逐顆die照自己的wafer_ring分配panel 0/1；超過兩種(目前介面只能表達2片)的
  話全部先歸在panel 0，並在狀態文字裡明確標注警告，不假裝處理得了；剛好一種(最常見的單一wafer情況)
  行為維持跟以前一樣
- 順便驗證了`wafer_ring`(如`FC2643`)就是FRM的Barcode ID、`.strate`自己的`mapping_lot`就是FRM的
  LotNo(用這個專案一路驗證下來的`WPQ5310156SS`/`FC2643`這組真實資料交叉確認)，所以載入範本時順便把
  兩片panel的「FRM Lot No」「Barcode ID」都自動填好，使用者各自按一次「自動讀取FRM檔案」就能把兩片
  wafer的圖都叫出來，不用手動查/打這兩個欄位
- 修正過程抓到一個相關小bug：panel 0(頁面靜態HTML)的FRM Lot No/Barcode ID欄位本來就有一組開發時期
  留下的預設值(`8P065800A1`/`T3DA62`)，第一版用「欄位是空的才填」防呆，結果被這組非空的舊預設值擋住
  填不進去——改成跟其他所有範本欄位一樣無條件覆蓋
- 用Playwright實際載入這份真實範本＋真實FC2643 FRM檔案驗證：224顆pick正確拆成49(FC2643)+175(FCEEB7)
  兩組、「跨兩片wafer」自動勾選、兩片panel的LotNo/Barcode ID都正確填好，FC2643那49顆pick座標全部落在
  該片真實wafer範圍內，沒有跑出界外
- 新增回歸測試`webapp/tests/test_app.py`的
  `test_api_parse_strate_picks_carry_the_real_per_die_wafer_ring_not_a_single_value()`，直接鎖定這份
  真實檔案「每一層都真的混著兩片wafer」這個事實，避免以後又退回「一層一片wafer」的簡化假設

## 疊層(一次上多顆，支援到8層以上)

2026/08/17：使用者提供了一份真實的**8層**`.strate`範例(`bingomap/tests/fixtures/
2070_V25NVDY_F2006908_20260702203138.strate`)，才發現原本以為「每多一層就要多一段
`DIE_INFO_OTHER_LAYERn`」的猜測是錯的——真實格式其實簡單很多：**`[DIE_INFO_BEG]`永遠只放
「目前這一層」(f9最大的那層)，其餘所有層全部混在同一段`[DIE_INFO_OTHER_LAYER_BEG]`裡，
靠每一列自己的f9(最後一欄)分辨屬於第幾層**——8層的例子裡，DIE_INFO放f9=8(7筆)，
OTHER_LAYER放f9=1~7(各7筆、共49筆)，照f9由小到大分組排列。這個發現讓`bingomap/strate.py`
完全不用改(它本來就是逐列讀f9、沒有假設同一段內f9是常數)，只要在`assignment.py`加一個
`assign_layers()`把N層通用地組出這個結構即可。

基本資訊區勾選「疊層(一次上多顆)」後，會多出「疊幾層」數字輸入框(預設2，最多16)。每層的f9
**自動編號1~N**(第N層＝目前層，寫進`DIE_INFO`；其餘層依f9由小到大寫進`DIE_INFO_OTHER_LAYER`)，
不用手動填f9。選座標區改成**同時顯示N張BINGO MAP**(各自獨立的格子圖、hover座標顯示、已選
清單)，用flex排版自動換行，不管幾層都排得下。

### wafer片數(1或2)跟疊幾層(N)是兩件獨立的事——2026/08/18修正

第一版把「疊N層」跟「N片wafer」寫死1:1綁定(第i層只能用第i片wafer的座標)，使用者實測後指出這是
錯的：**疊幾層(N)完全由物理上的die-attach堆疊決定，跟座標來自幾片wafer無關**——不管疊2層還是
8層，座標可能全部來自同一片wafer，也可能來自兩片不同的wafer，但「這是第幾層」永遠不該取決於
「這是第幾片wafer」。

修正後的操作方式改成**「先選wafer座標→點進哪一層的BINGO MAP才寫入哪一層」**兩步驟：

1. 在wafer圖上點一格＝**選取(待寫入)**該座標(橘色虛線框)，還沒有指定要進哪一層；拖曳一個矩形＝
   一次選取一整批(整批一起待寫入)。再點一次已選取的格子可以取消選取。
2. 選好之後，點下方**任一層**的BINGO MAP(格子區域)，就會把目前所有「待寫入」的座標整批寫入
   點的那一層，跟座標原本是從哪一片wafer選的沒有關係。已寫入的格子統一用藍色實線框+格內數字
   標示是第幾層(不是每層配一種顏色，N到8層以上顏色會分不清楚)。
   - 如果目前沒有任何待寫入的座標，點BINGO MAP格子會退回原本的「反查」功能：查這格對應到哪個
     wafer座標(在wafer圖上用橘色實線框標示)。
   - 「標記『不上片』模式」開啟時，點BINGO MAP格子永遠是標記/取消不上片，優先權比待寫入寫入
     還高。

這個設計直接解決了使用者最早反映的「切換層很容易點錯」問題——目標層不是靠一個容易忘記切換的
按鈕決定，而是**點下去的當下**才決定要寫入哪一層，寫錯層的機會小很多。

**跨兩片wafer**：勾選「跨兩片wafer」後固定多出**一個**額外的wafer讀取區塊(FRM或貼文字都獨立
一份)，畫面同時顯示兩張wafer圖，兩張圖都可以直接選取待寫入的座標，選完點哪一層的BINGO MAP
就寫入哪一層——**跟疊了幾層完全無關，固定就是2片**(不會因為疊8層就變成8片wafer)。已經在某一
片wafer上寫入過的座標，全域(不論哪一層)不能在**同一片**wafer上重複選取；但兩片wafer之間即使
座標數值相同也不算重複，因為是不同的實體wafer。

**「跨兩片wafer」不需要先勾選「疊層」**(2026/08/18修正)——第一版把這個勾選框藏在「疊層」
底下，沒勾疊層就看不到、也用不了，但使用者指出跨兩片wafer的需求在**只有第1層(完全沒有疊層)**
時一樣會發生(例如第一片wafer好的顆數不夠填滿，要換第二片wafer繼續選)。現在這個勾選框永遠
可見、可以獨立勾選，跟「疊層(一次上多顆)」勾選框互不影響——沒疊層時勾了會多出第二張wafer圖，
兩張圖選的座標最後都寫入唯一的那張BINGO MAP；疊層時則跟前面說明的一樣，寫入哪一層由點哪個
BINGO MAP決定。

**注意**：更改「疊幾層」數字或切換「跨兩片wafer」勾選框，都會**清空目前已選的座標跟wafer
資料**，重新產生對應設定的畫面結構——這是刻意的簡化設計，沒有嘗試把舊設定的資料重新對應到
新設定，避免猜錯映射關係。建議先確定好要疊幾層、要不要跨兩片wafer，再開始選座標。

（修過的bug：先勾「跨兩片wafer」、再載入.strate範本，第二張wafer圖會無聲無息消失——
`loadTemplate()`原本不管使用者當下設定為何，一律把「跨兩片wafer」強制重設成關閉，跟「wafer片數
是使用者獨立設定、不該被其他動作覆蓋」這個原則互相矛盾。已經修好：載入範本不再動「跨兩片wafer」
的狀態，維持使用者原本的設定；不論先勾選再載入範本、還是先載入範本再勾選，都能正常運作。）

wafer圖跟基板圖(bingomap)滑鼠移到格子上時，除了原本上方的文字狀態列，格子正上方也會浮出一個
跟著游標的座標提示框，不用把視線移到畫面上方找狀態列。

（修過的bug：第二個wafer面板的「自動讀取FRM檔案」按鈕原本按下去完全沒反應——`loadFrmInto()`用
樣板字串組狀態文字元素的id時，因為那個id剛好是連字號命名而不是底線命名，組出一個不存在的id，
`getElementById`拿到`null`直接讓函式在第一行就拋例外，連fetch都沒發出去，畫面上什麼提示都不會
顯示。已經修好並用Playwright驗證錯誤訊息會正確顯示紅字、成功載入也會正確渲染出wafer圖；這次
N層重構把每個wafer面板的id都改成統一規則產生，不會再有這種手動組id漏改的風險。）

## Wafer圖bin顏色（依實際出現的bin code動態上色）

原本wafer圖只分兩色：綠色＝Bin 1、粉紅色＝「其他所有bin」全部同一色，這是最早只用單層/雙層測試資料
時順手寫的簡化版本。2026/08/19使用者用STRATE補檔頁跑真實SECS log的wafer圖，發現「應該依據下載下來
有什麼bin code就出現，不能只有Bin 1 Bin 7」——真實資料裡同一片wafer常常同時有好幾種bin(例如
2/6/7)，全部混在「其他」同一個粉紂色看不出差異。

改成依實際bin code動態上色：固定一份0~9的10色調色盤（bin值一律是單一ASCII數字——見
`bingomap/frm_reader.py`的`_decode_bin_kind()`，`int(chr(value))`只有單一十進位數字才會成功，這是從
反編譯`WaferCoordinate.exe`得到的格式規格，不是猜的），bin 1維持原本綠色、bin 7維持原本粉紅色（沿用
使用者已經熟悉的顏色），2~6/8/9另外配色，圖例只列出**目前這份資料實際出現過的bin code**（不是固定
列出全部10種），三個有wafer圖的頁面（①補資料、②誤吸偏移／BIN點除、④STRATE補檔）都是同一套
`BIN_COLORS`/`binColor()`/`applyBinColor()`(各自檔案裡各自維護一份，是這個專案一貫的小工具函式重複

## 參考基板的清除按鈕太遠、沒有legend——被誤認成「清不掉的殘留資料」

2026/08/25使用者回報：載入wafer之後，wafer圖上出現一大片跟真正bin顏色無關的彩色字母格子，按「清除
待寫入的座標」「清除已載入的Wafer MAP」都沒有反應。查證後這些字母格子其實是「參考同一片wafer的其他
基板」功能畫出來的參考基板占用座標(唯讀，不能選取，見上面`referenceLetter()`那段程式碼)——這個功能
連同它的清除按鈕(`btn-clear-references`)、圖例都只放在頁面最上方「複製既有.strate為範本」那個區塊，
離wafer圖很遠；而且它的資料會被`restoreState()`自動存進localStorage、下次開頁面自動還原，使用者換了
新wafer但沒特別想到要往上滑去清舊的參考基板，看到不明字母格子覆蓋畫面，會合理地以為是bug——而且他按
的另外兩顆清除鈕本來設計上就不會動到參考基板(各自清不同的資料)，難怪按了「沒反應」。

修正：不改變參考基板本身的清除邏輯(仍然是同一個`clearReferenceSubstrates()`)，而是在wafer圖旁邊
(Wafer Bin資料區塊裡)新增一份完全同步的圖例＋「清除參考基板」按鈕複本(`wafer-reference-legend`/

另外兩顆清除鈕清不掉它。原本上方的按鈕/圖例原封不動保留，兩邊用`updateClearReferencesVisibility()`
同步顯示狀態。

教訓：**功能本身沒有bug，是「同一個畫面問題，控制它的按鈕卻在很遠的地方，而且會被瀏覽器自動記住、
無聲無息地跨工作階段殘留」——使用者在問題發生的現場(wafer圖旁邊)找不到對應的解法，會直接判定成
「清除按鈕壞了」，即使個別按鈕各自都照原本設計正常運作。這類UX問題不能只看「程式邏輯對不對」，要看
「使用者遇到問題的當下，能不能在畫面上找到答案」。**

## Wafer圖方向（X/Y軸反轉）——不同layout需要的方向不一樣，改成手動切換

2026/08/20用WPQ5310156SS/FC2643這片wafer(EU014 layout)反覆驗證過：wafer圖畫面上**X軸要反轉(欄0在
右邊)、Y軸不轉**，才會跟真正的WaferCoordinate.exe/目視檢查吻合，而且不只一次確認過(色碼核對、T點
公式反推、逐格核對)。2026/08/21使用者換了另一片真實wafer(FQFYMFS.5X/J7697F，layout MS040)重新測試，
畫面上的粉紅色(bin7)團塊位置跟真正的WaferCoordinate.exe看起來不一樣。

第一次判斷判錯了方向：先拿使用者回報的一組座標(position(24,26)=bin7)去反查`.frm`的`die_map`，算出
「X軸不轉、Y軸反轉」對得上，就把這個結論當成答案。**這個結論後來被使用者直接推翻**——把三張真實
畫面(我們自己畫的圖、目視檢查、WaferCoordinate.exe)並排比對後，使用者明確指出正確答案其實是
**「X軸反轉、Y軸也反轉」(兩個勾選框都打勾)**，前一次靠單一座標反推出的「X不轉/Y反轉」是錯的——
單一(position, bin)配對能拿來排除明顯不合的組合，但不足以取代整張圖的視覺比對，這次的座標反推本身
可能哪裡算錯了(還沒查出確切原因)，直接採信使用者拿三張真實畫面比對出的結論。

這代表：**EU014需要「X軸反轉、Y軸不轉」，MS040需要「X軸反轉、Y軸也反轉」(兩個都勾)，不是簡單的
「兩片wafer方向相反」，也不是只靠单一座標反推就能保證找對**。試着找兩片wafer之間有什麼欄位可以分辨
方向(檢查過`.frm`檔案自己的`reverse_fixed`欄位，兩片都是`2`，看不出差異；MS040的`F:\SMAP\MAP\MS040`
檔案裡`Flat=0`，代表WaferCoordinate.exe自己的旋轉機制沒有被觸發，也不能解釋這個差異)——目前沒有找到
任何一個可靠、機讀的欄位可以事先判斷該用哪個方向。

**結論：跟T點最後變成手動輸入是同一個教訓——沒辦法用單一公式套用到全部wafer，改成手動切換，不再
猜一個「應該適用全部wafer」的規則**。①補資料頁(每片wafer panel各自)、②誤吸偏移／BIN點除頁都新增了
「X軸反轉」「Y軸反轉」兩個勾選框，預設是原本驗證過的方向(X反轉/Y不轉)，不會讓舊資料無聲無息跑掉；
遇到畫面跟WaferCoordinate.exe對不上的wafer，直接切換勾選框試哪個組合能讓bin7/bin1分布吻合即可，
**判斷方式以直接拿整張圖跟真實畫面並排比對為準，不要只靠單一座標的bin顏色反推去下結論**。這只改變
畫面上格子的排列順序(哪個欄/列顯示在哪個位置)，dataset裡每一格的原始座標值完全不受影響，已經選取/
待寫入/已寫入某一層的座標不會因為切換方向而跑掉或重算錯。

## 換一片wafer要重設X/Y軸反轉勾選框，不能沿用上一片的設定

2026/08/25使用者用另一片wafer(8P964000A1，機型DIE系列，layout AW191)測試時反映：「雖然我可以設定
角度轉向，但是我的座標不要改也跟著轉，我的座標應該都是固定右上角都是0,0才對」。查證後發現：X/Y軸
反轉勾選框是每個wafer panel的即時DOM狀態，載入新的wafer資料(FRM或貼文字)時完全不會被重設——如果
使用者為了對某一片wafer(例如前面提到的MS040)才手動把Y軸反轉打勾，之後在同一個瀏覽器分頁換載入另一
片完全不同的wafer，勾選框會原封不動留著，新wafer的0,0就這樣被「上一片wafer調過的設定」帶去了不是
使用者要的角落——不是使用者主動為這片新wafer做的選擇，是設定不小心沿用下來的。

修正：①補資料頁的`loadFrmIntoPanel()`(自動讀取FRM)、「載入Wafer地圖(文字)」按鈕、「清除已載入的
Wafer MAP」按鈕，②誤吸偏移頁的`previewWaferMap()`，全部在載入/清除新wafer資料時呼叫`resetWaferFlip()`
(app.js)把該panel的X/Y軸反轉都重設回預設值(X反轉/Y不轉＝座標0,0固定在右上角)，勾選框本身的DOM
`checked`狀態也一併同步重設，不會停留在上一次操作留下的畫面。需要為某片特定wafer調整方向，要在
「載入」**之後**再手動勾選——這個手動調整只對目前這次載入有效，換下一片wafer會自動清掉，不會帶著走。

教訓：**手動切換選項(這裡是X/Y軸反轉)如果沒有明確的生命週期(什麼時候該重設回預設)，很容易在使用者
換了操作對象(這裡是換了一片wafer)之後被誤用成「上一次操作」的殘留設定，而不是「這一次操作」的
主動選擇。凡是新增一個手動切換的選項，都要同時想清楚：什麼動作應該讓它重設回預設，不能只做「加一個
checkbox」就結束。**

## Wafer圖方向最終改版：X/Y軸反轉勾選框整個拿掉，改成0/90/180/270度角度選單

2026/08/25使用者對上面「重設勾選框」那個修正版仍然不滿意，直接指示：「我要的是右上角永遠固定0，0，
wafer角度你只要0，90，180，270度讓我可以選擇轉向，你現在做的都不是我要的」。這句話點出X/Y軸反轉
勾選框從一開始的設計就有根本缺陷：它只改變畫格子的**顯示順序**，dataset.x/y用的還是FRM原始座標，
所以「0,0在右上角」從來不是結構上保證的——勾選框湊出的四種組合裡，只有一種(預設值)剛好是0,0在右上角，
其他三種都不是，使用者稍微調整或勾選框沒被正確重設，0,0就跑掉了。這解釋了同一天稍早那次「重設」修正
為什麼還是不夠：重設只是讓預設值*剛好*對，沒有讓「0,0永遠在右上角」這件事本身變成結構性保證。

**新設計**：拿掉X軸反轉/Y軸反轉兩個勾選框，改成單一的「wafer角度」下拉選單(0°/90°/180°/270°)。
畫格子的排列順序**永遠固定**(欄0在右邊、列0在最上面，不再是可切換的選項)，角度選單則是**直接重新
計算每一顆die的座標**(`rotateWaferCells()`，app.js；`rotateWaferArray()`，mispick.js——兩邊各自
維護一份相同公式，因為兩個檔案沒有共用模組機制)，把原始(x,y)正規化成0-based的(u,v)後套用標準90度
旋轉矩陣，再重新组裝成新的(x,y)標籤——這組**重新計算出來的座標才是「真實」座標**，會被staging/
已寫入/複製出去的座標文字使用，不只是換個顯示順序而已。因為畫格子順序是固定的、且旋轉公式本身保證
「新座標的(0,0)套用固定順序後一定落在右上角」(旋轉後直接照0..新寬度-1／0..新高度-1的範圍鋪滿，跟
旋轉前的座標系統無關)，所以0,0永遠在右上角是**結構上保證**的，不是「預設值恰好對」。0°時就是原本
「X反轉/Y不轉」驗證過的行為(EU014/FC2643那組真實資料)，不會讓舊資料跑掉；90°/270°時畫面的寬高會
互換(例如71x44的wafer轉90度後顯示變成44x71)，這是矩形wafer轉90度的預期結果，不是bug。

**②誤吸偏移頁的角度只影響畫面預覽/複製座標文字**，不影響實際的誤吸偏移分析結果——分析(`/api/mispick/
analyze`)完全在後端用既有的DB/ESEC座標公式計算，前端沒有把角度傳給後端，是兩個獨立的系統，這點在改版
前就已經是這樣，改版沒有動到。

實測驗證(Playwright)：載入MS040那片wafer(71x44)，四個角度分別確認欄標題最右邊都是`0`、列標題最上面
都是`0`(0,0永遠在右上角)，90°/180°/270°畫面截圖確認bin7的粉紅色團塊真的跟著旋轉(不是只換了標籤沒換
圖案)，90°時畫面維度正確互換成44x71。

教訓：**這是同一個功能第三次修正才收斂(先是勾選框本身、再是重設時機、最後才是整個機制拿掉重做)，
回頭看，前兩次修正都是在「盡量不動既有設計」的前提下打補丁，但使用者要的其實是一個**結構上不會出錯**
的設計，不是「預設值調對、記得重設」這種靠人為紀律維持正確性的方案。當使用者用「你現在做的都不是我
要的」這種話明確否定整個方向時，不要再嘗試在原本的設計上打第三個補丁——這通常代表原本的設計思路本身
就跟使用者要的東西不是同一件事，該做的是照使用者給的新設計直接重做，而不是繼續修修補補。**

### 同一天：④STRATE補檔頁也套用同一套角度選單

改完①②兩頁之後使用者接著說「其他分頁也一樣」。查了一下，④STRATE補檔 XML合併頁(`strate_xml.js`)的

排列順序原本就已經是寫死的固定順序(欄0在右邊、列0在最上面，這頁一開始就沒有X/Y軸反轉勾選框可以調)，
所以「0,0在右上角」本來就結構上成立，但沒有辦法應付「這片wafer的真實方向就是跟log解析出來的不一樣」

那樣的真實wafer絕對座標，套「角度選單」的概念在這裡意義不明確，所以先不改；如果使用者其實也是指這頁，
需要使用者確認想要的是什麼(例如：想調整的是最終算出來的FX:FY絕對座標的方向，還是這個相對座標預覽圖
本身的顯示角度)。

標示(紅底"A"字)跟着wafer形狀一起轉、位置仍對齊沒有錯位。

### 同一天：角度選單旁邊加了「鏡像」勾選框——旋轉湊不出鏡像效果

使用者拿①頁畫面跟真正的WaferCoordinate.exe並排比對後，回報畫面是**鏡像**的，要求「幫我把圖檔改成
鏡像」。這點出一個數學上的事實：角度選單只能做**旋轉**(0/90/180/270度4種)，旋轉是保留手性(chirality)
的對稱操作——不管轉幾度，圖案的鏡向都不會變；鏡像則是相反手性的對稱操作，兩者是不同類的變換，4個
旋轉角度不管怎麼組合都湊不出鏡像的結果。如果使用者比對出來的真實方向剛好是鏡像關係，光靠角度選單
無論如何都對不上。

修正：①②④頁的角度選單旁邊都加了一個獨立的「鏡像」勾選框。跟角度選單一樣，鏡像也是重新計算座標
(不是換顯示順序)——先套用選好的角度算出旋轉後的座標，勾選鏡像的話再對這組座標做一次水平翻轉
(`rotateWaferCells()`/`rotateWaferArray()`/`rotateWaferMapAndSubstrates()`三個檔案各自維護同一條
公式，函式簽章都改成多收一個`mirror`布林參數)。角度(4種)+鏡像(2種)合起來湊出全部8種可能的方向，
數學上對應矩形的完整二面體對稱群(dihedral group of order 8)，理論上足夠涵蓋任何真實wafer可能的擺放
方向。跟角度選單一樣，換一片新wafer時鏡像勾選框也會自動重設回不勾選，不會被上一片wafer調過的設定
帶到新wafer上。

教訓：**「這個功能還缺什麼」有時候是數學問題，不是猜漏了哪個選項——這次不是「4個角度不夠多、該加
到8個角度」，而是「角度」跟「鏡像」根本是兩種不同的對稱操作，缺的是另一整個維度，不是同一個維度裡
的更多選項。遇到「調了每個選項都對不上」的回報時，值得先確認一下：現有的選項集合在數學/幾何上是否
真的涵蓋得了對方要的那個結果，而不是預設「一定是某個組合我還沒試」。**

  `saveState()`修正。

## 參考同一片wafer的其他基板

同一片實體wafer常常會切成好幾枚基板，各自產生各自的`.strate`。「複製既有.strate為範本」欄位下方
另外有一個「參考同一片wafer的其他基板（選用，可多選）」區塊（`#reference-files`，`<input type=file
multiple>`），可以**一次選多個**已經完成的`.strate`檔案，純粹當「參考」疊在wafer圖上——**不會**被
編輯或合併進正在做的這一枚（跟上面「複製既有.strate為範本」是完全不同的動作：範本是把一份檔案的
座標跟基本資訊整個載進來繼續編輯／重新產生；參考檔案的座標只拿來畫在wafer圖上、擋掉重複選取，
它本身的基本資訊完全不會影響目前正在填的表單）。

行為（2026/08/18跟使用者用AskUserQuestion確認過）：
- 參考檔案佔用過的wafer座標，**直接擋掉不能再被選取**——不管是單點還是拖曳矩形選取都一樣，
  跟「已經寫入某一層」的座標擋法完全相同（`isReferencedAt()`），避免跟其他基板選到同一顆wafer die。
- wafer圖上會**分辨是哪一枚參考檔案**佔用的，不是統一畫成一種「已佔用」標示：每個檔案有自己的
  顏色＋字母代號（A、B、C…，超過26個之後改用R27、R28…），格子背景色＝那個顏色、格子文字＝那個
  字母，滑鼠移過去的提示文字跟浮動tooltip也會顯示是被哪一枚基板（SUBSTRATE_ID）佔用的。旁邊的
  `#reference-legend`會列出每個代號對應到哪個基板ID、佔用幾顆。
- 參考檔案的座標一律套用在**第一片wafer(panel 0)**——參考檔案本身沒有「這是第幾片實體wafer」的
  概念(跟「複製既有.strate為範本」載入的座標一樣，都假設是panel 0)，這也符合「參考同一片wafer的
  其他基板」這個功能本身的前提：本來就是同一片實體wafer才需要互相參考擋重複。
- 參考資料是獨立於「疊幾層」「跨兩片wafer」「載入範本」「產生空白骨架」之外的資料——切換這些設定
  都不會清掉已載入的參考基板列表(用Playwright驗證過)，因為它描述的是wafer本身的既定事實，跟目前
  在編輯哪個設定/哪一層無關。要清掉就按「清除參考基板」按鈕(`#btn-clear-references`)。
- 參考檔案的解析沿用既有的`/api/parse_strate`(逐一呼叫，前端迴圈處理多個檔案)，取每個檔案
  `layer_picks`攤平後的全部座標(涵蓋該檔案自己的所有疊層)當作佔用範圍——沒有新增後端API。

## 切換分頁資料不遺失（五個分頁都已支援）

2026/08/18 STRATE補檔頁最早做了這個（見下方該節），2026/08/19使用者反應「每個分頁在切換的時候資料
不要不見」——確認除了STRATE補檔跟SECS格式化參數頁，其餘三頁(①補資料/②誤吸偏移/③Crack位置回推)還
沒補上，這次補齊，五個分頁現在都用同一套`localStorage`慣例：存的是**已經處理過的結果**(表單欄位值、
已解析的檔案內容、已選取的座標等)，不是原始檔案本身(瀏覽器基於安全性不允許用JS把檔案塞回
`<input type=file>`)，重新整理/切換分頁回來後自動還原、不用重新上傳。

- **①補資料（`app.js`）**是資料量最大、狀態最複雜的一頁（多層/多wafer/待寫入座標/已選參考基板…），
  做法是把`saveState()`掛在`renderAll()`最後一行——這個專案裡幾乎每個會改動狀態的操作最後都會呼叫
  `renderAll()`重繪畫面，掛在這裡等於自動涵蓋所有現有跟未來新增的操作，不用在每個按鈕/點擊事件各自

比對驗證過完全一致」的同一份參考檔案)當範本，疊在WPQ5310156SS/FC2643這片wafer的真實bin圖上，
「已寫入」的座標散得到處都是、明顯超出wafer範圍——使用者一開始以為是wafer圖本身鏡像了，要求重新
確認方向。這次沒有再猜，直接拿使用者這份`.strate`裡FC2643的49顆die座標，跟FC2643真正的`.frm`檔案
(die_map)逐顆交叉比對：

- **原封不動比對(`wafer_xy`當作x:y直接查)**：49顆裡只有35顆(71%)真的落在bin=1的位置，8顆完全落在
  wafer外圍的空白區、4顆對到bin=6(壞的)、1顆對到bin=2(壞的)、1顆對到bin=7(壞的)——但這份`.strate`

  跟`.strate`自己說的「全部都是良品」完全吻合，不是巧合

追根究底找到真正的成因：**回頭看SECS log自己原始的`<DIE_INFO>`XML內容**(不是我們解析出來的結果，
是log檔案裡的原始文字)，第一顆die就寫著`FC2643,15:5,0:0,...`——跟上面比對"互換"之後才對的上的
座標完全一致，證實**這不是我們的解析程式改動或算錯的，是機台SECS log自己記錄`<DIE_INFO>`的
`wafer_xy`欄位時，用的就是`row:col`(列在前、欄在後)**。但`.strate`檔案格式本身的`wafer_xy`約定，
是`col:row`(欄在前、列在後——這是2026/08/17用另一片完全不同的真實DB案例
`2070_V32AWE6_Z26306101030_...`驗證過的，見`bingomap/tests/test_mispick_analysis_real_db_sample.py`)。

`secs_log.py`的`extract_strate_files()`原本是把log的`<DIE_INFO>`文字**原封不動**複製進`.strate`
輸出(docstring原本寫的就是`DieInfo.from_line()`直接解析、不改內容)——這正是問題所在：log自己的
`row:col`欄位順序，被誤當成`.strate`格式標準的`col:row`直接寫出去，語法(9欄CSV格式)完全對，但欄位
**語意**(每個數字代表的軸)反了。上面那次「逐行byte-for-byte比對驗證過完全一致」的驗證，比對的
參考檔案剛好也是同一種方法產生的(同樣沒做欄位互換)，兩邊「一致」只是因為犯了同一個錯，不是真的
驗證過跟機台原生`.strate`格式相符。

至於`WaferStart`的`BinList`(用來畫這頁自己的wafer圖)：`wafer_map_from_element()`內部本來就是
「以log的原始row:col為準」在存(`row index = wafer_xy的第一個數字`)，跟`DIE_INFO`用的是同一種
log原生語意——這頁的疊圖(基板占用位置疊在wafer圖上)之所以能對上、94~96%吻合，是因為**兩邊都用
log原生的row:col語意，內部自己一致**，不代表這個語意就是`.strate`格式該用的col:row。

**已修正**：
- `bingomap/secs_log.py`新增`_swap_wafer_xy()`，`extract_strate_files()`輸出的每一筆`DieInfo`的
  `wafer_xy`都會從log原生的row:col換成`.strate`標準的col:row——下載/複製到①補資料／②誤吸偏移／
  ③Crack位置回推當範本，現在都會落在正確位置
- `wafer_map_from_element()`同步把`WaferBinMap`內部存法也改成`(x=欄,y=列)`，跟`frm_reader.py`的
  `die_map`、跟整個網站其他頁面的wafer座標慣例一致(先前是`(x=列,y=欄)`，只有這個功能自己用反的)
- `strate_xml.js`的`renderWaferGrid()`跟著同步改成「x=欄(水平)、y=列(垂直)」，畫面排版(哪個軸畫
  水平/垂直)完全沒變，只是底層資料語意跟著訂正
- `SECS_T_POINT`常數從`{x:14,y:45}`改成`{x:45,y:14}`——巧合的是，這剛好跟①補資料頁2026/08/20
  用完全獨立的另一組真實資料(目視檢查Ref.Point換算DB規則)反推出來的公式一致：
  `T點X=columns−Ref.Y=46−1=45`、`T點Y=rows+Ref.X=24+(−10)=14`，兩條完全不同的調查路線得到
  同一個答案，互相佐證這次的修正方向是對的
- 新增回歸測試`bingomap/tests/test_secs_log.py`的
  `test_extract_strate_files_wafer_xy_matches_real_frm_die_map()`：直接拿使用者提供的真實
  `.strate`(49顆FC2643 die)跟真實`.frm`(FC2643的die_map)交叉比對，鎖定「互換後49顆全部對到
  bin=1、無重複」這個結果，不會再退回去
- 用Playwright實際重跑一次使用者原本回報的情境(用修正後的.strate當①補資料頁範本，疊在WPQ5310156SS
  wafer上)：56顆「已寫入」座標全部落在wafer內部的綠色區域、緊密聚在一起，不再散落到wafer外圍

教訓：**「逐行byte-for-byte比對驗證過完全一致」聽起來很嚴謹，但如果拿來比對的參考資料本身也是
同一套(有問題的)邏輯產生的，兩邊「一致」只是同一個錯誤的兩份拷貝，不代表真的驗證過格式正確——
要驗證，必須拿完全獨立、不同來源、不同方法產生的真實資料交叉比對(這次是反過來用真正的`.frm`
die_map去對，而不是自己另一份`.strate`跟自己比)，才能真正抓出語意層面(不是語法層面)的錯誤。**

### 後續更正：上面的swap結論整個是錯的——兩個獨立、方向相反的bug互相抵消，讓swap看起來通過了驗證

2026/08/26使用者回報STRATE補檔救回來的檔案在①補資料頁還是會跑到wafer外圍，這次一次給了兩份完全
獨立的真實資料：同一台machine對同一枚基板(`Z25709007096`)產生的真實log
(`BAB1420260801_04.0.log`)**跟**真正的`.strate`檔案，可以直接互相比對，不用像上次一樣繞道查`.frm`。
結果：log的`<DIE_INFO>`/`<DIE_INFO_OTHER_LAYER>`的224行`<Item>`文字，跟真正`.strate`檔案自己的
DIE_INFO逐行**完全一致，一個字都沒有不一樣**——`wafer_xy`本來就已經是`.strate`格式的`col:row`，
上面那次做的`_swap_wafer_xy()`從頭到尾是不需要的，而且是**有害的**：把本來就對的資料又轉了一次，
變成錯的。

上面那次的`.frm`交叉比對(49顆FC2643的die，互換後49/49對到bin=1)為什麼還是得出錯誤結論？因為那次

`x, y`存進`die_map[(x,y)]`——但這個命名本身就是誤導，`die_map`真正的key其實是`(row,col)`，不是

wafer_xy、用`frm.die_map.get((col,row))`查」——兩個方向相反的獨立錯誤疊在一起，數學上剛好互相抵消，
讓swap之後的結果看起來完全通過驗證，實際上是兩個錯的東西湊出一個巧合的對。

**已修正**：
- `_swap_wafer_xy()`整個刪除，`_die_list()`直接用log原始的`wafer_xy`，不做任何轉換
- `wafer_map_from_element()`：log的`<ColCount>`/`<RowCount>`標籤名稱本身也跟`.strate`的col/row軸向
  對調(跟`frm_reader.py`的`x,y`誤導性命名同一種問題)，建構`WaferBinMap`時已對調成
  `columns=RowCount, rows=ColCount`，`BinList`的chunk索引/字元位置指派也跟著對調
- 新增回歸測試直接比對「真實log」vs「真實.strate」逐行byte-for-byte相符——這比之前「swap後對到FRM
  bin=1」更直接，不透過任何中間轉換或查表，兩份獨立真實資料直接比對，沒有讓兩個bug互相抵消的空間

教訓：**兩個獨立的欄位語意bug，只要方向相反，套用在同一份資料上會互相抵消，讓其中一個(甚至兩個)
都看起來通過了「跟真實資料比對」的驗證——這比「參考資料本身也有同一個錯」更隱蔽，因為這次用來比對
的`.frm`確實是真正獨立的第三方資料，理論上足以抓到問題，卻因為驗證鏈路中另一個環節(`frm_reader.py`
的die_map key順序)也帶著錯，讓兩個錯互相掩護。避免這個陷阱的關鍵是盡量縮短驗證鏈路：與其比對
「A轉換過的結果」對「B查表出來的結果」(兩邊都可能各自帶錯)，不如直接比對兩份完全獨立、沒有經過
任何己方轉換的真實資料原始輸出，中間環節越少，能藏兩個互相抵消的bug的空間就越小。**

### 再後續更正（2026/08/27）：`frm_reader.py`自己的`die_map` key順序bug，這次真的修了

照指示重新交叉比對，這次用**三個完全獨立的來源**確認`die_map`的key順序問題是真的、而且必須修：
1. 前面已經有的49顆FC2643真實die(`.strate`已知col:row、已知bin=1)：不對調key只有35/49(71%)對得上，

## SECS格式化參數（`/secs-params`）

2026/08/19使用者要求「機台內secs參數與excel檔案的參數去比較」。2026/08/20使用者提供了真實的目標

每個`Item`是一項參數——`<CCODE>`(數值編號，同一份快照內唯一)加上固定6個`<PPARM>`欄位(名稱/單位/
格式代碼/目前數值/下限/上限)。解析邏輯在`bingomap/secs_params.py`，遇到不是剛好6個`PPARM`的Item會

畫面：上傳log(跟STRATE補檔頁同一套base64上傳/`localStorage`還原機制)、按「解析Log」，每一次快照各自
一張表格(CCODE/名稱/單位/格式/數值/下限/上限)，可以個別下載CSV。

**2026/08/19新增匯出功能**（使用者要求「這些後續要可以匯出excel或者txt檔」）：

  （見下面②，還沒做），基準本身不需要每次重新從log算

  而不是`PPParamSnapshot`物件)，這樣基準清單(JSON dict)跟從log現場解析出來的快照可以共用同一套
  匯出程式碼，不用維護兩份幾乎一樣的邏輯

**2026/08/19開發途中發現並修正一個解析bug**：`secs_log.py`跟`secs_params.py`原本的
`_TRANSACTION_RE`正則式`<Transaction\b[^>]*>.*?</Transaction>`沒有考慮自我封閉標籤
`<Transaction ... />`(每一個Request那半，內容都是空的、用自我封閉標籤寫)——正則式的`[^>]*>`會把
`/>`誤認成一般開始標籤的`>`，接著非貪婪的`.*?</Transaction>`就會一路吃到**下一個**Transaction的
結束標籤才停，把兩個不相干的Transaction黏成一段無效XML，`ET.fromstring`解析失敗後兩個都被跳過——
平常log裡Request跟它自己的Reply中間通常還夾著別的Transaction(有自己的結束標籤讓正則式提早停下)，
不容易踩到，但TID=58203這組偏偏是Request後面緊接著自己的Reply、中間沒有別的Transaction，直接把
第二筆199組參數的快照整個吃掉、不留任何錯誤訊息(從API回應完全看不出「有一筆不見了」)。修正成
`<Transaction\b[^>]*/>|<Transaction\b[^>]*>.*?</Transaction>`(先試著整段匹配一個自我封閉標籤，不行
才退回找配對的結束標籤)，兩個模組都已修好，測試fixture也重建成刻意保留「Request緊接自己Reply、中間
沒有其他Transaction」這個真實排列方式，鎖定這個bug不會再發生。這個bug理論上也可能在STRATE補檔頁的
`StrateMap`/`WaferStart`資料上發生(同一份`_TRANSACTION_RE`)，只是這份真實log剛好沒踩到(每次都有別的
Transaction夾在中間)——已經修好，不用等真的漏資料才發現。

## 誤吸偏移頁：STRATE檔案分好幾次選會互相蓋掉，改成累加

2026/08/25使用者回報：「誤吸偏移這個為什麼只能一個檔案load進去，再換下一個檔案都沒反應」。查證後這是
`<input type="file" multiple">`的原生行為，不是我們程式邏輯的問題——只要不是在**同一次**選擇檔案視窗
裡用Ctrl/Shift一次選好幾個檔案，而是分好幾次打開「選擇檔案」視窗、每次只選一份，瀏覽器每次都會把
`.files`整批換掉，不會累加。原本`analyze()`直接讀`input.files`，所以分好幾次選檔案時，只有最後一次
選的那份會留下來，前面選過的檔案就這樣不見了，使用者會以為是「換檔案沒反應」。

修正：不再由`analyze()`直接讀取`input.files`，改成監聽`change`事件，把每次新選到的檔案(用檔名+大小
去重複)累加進`pendingStrateFiles`陣列，並在檔案選擇欄位下面列出目前已經加入的所有檔案，每份都可以
個別按「移除」，也有「清除已選擇的STRATE檔案」整批清空。`input`本身每次`change`後清空`value`，這樣
就算使用者重複選到同一份檔案，也還是能正常觸發`change`(瀏覽器對「選到同一個檔案」預設不會觸發
change，清空value可以繞過這個限制)。`analyze()`改成從`pendingStrateFiles`組出要送出的STRATE內容，
不再依賴`input.files`目前這一刻裝了什麼。

教訓：**`<input type="file" multiple">`只保證「同一次選擇視窗裡可以選多個」，不保證「跨多次選擇視窗
會累加」——這是很容易被忽略的HTML規格細節，尤其當使用者的直覺用法是「每次只選一份、分批加入」而不是
「一次全選」時，原生行為會悄悄把之前選的都丟掉，而且沒有任何錯誤訊息或提示，看起來就像「功能壞了」。
凡是允許多檔案上傳的介面，都要明確決定並讓使用者看得到：到底是「每次選擇都是全新一批」還是「累加」，
不能靠瀏覽器預設行為，也不能假設使用者知道這個規格細節。**

## 誤吸偏移頁：機台偏移量要能是0(T點沒有偏移)，且T點預覽圖要能直接看出偏移前後的差異

2026/08/27使用者回報兩個問題：(1)「機台偏移量」欄位跳過0(從1直接跳到-1)，但「如果T點沒有偏當然就是0，
T點偏移才會有(1:0)(-1:0)(0:1)(0:-1)」——0本身是一個有意義、應該可以選的狀態(代表沒有偏移的基準情況)，
不該被當成不合法輸入拒絕；(2)「數值變T點圖也要跟著變才對，改成有兩個圖左邊是正常(0:0)T點沒偏移，
右邊圖是數值變動，T點圖形就要偏移」——原本的T點預覽只有一張圖，換偏移量並不會讓T點標記跟著移動，
看不出偏移實際會讓T點落到哪裡。

查出0被拒絕是刻意設計：`bingomap/mispick_analysis.py`的`make_offset()`一開始就寫死
`if value == 0: raise ValueError(...)`，前端`mispick.js`的方向微調按鈕(`nudgeOffset()`)也配合這個
限制，算出0的時候會強制改回±1(`next === 0 ? delta : next`，註解直接寫「offset must never be 0」)。
這個限制本身沒有真實資料佐證，純粹是最初設計時「反正要分析就一定要有個偏移量」的假設——但`Offset.axis`
除了顯示之外(`analyze_substrate()`只用到`offset.dx`/`offset.dy`，兩者用value算，跟axis無關)並不影響
分析邏輯，value=0時dx=dy=0，等於「不偏移」的identity情況，本來就是分析邏輯可以正常處理、有意義的
一種狀態。

已修正：
- `make_offset()`拿掉0的限制，`bingomap/tests/test_mispick_analysis.py`的
  `test_make_offset_rejects_zero`改成`test_make_offset_allows_zero`確認dx=dy=0；
  `webapp/tests/test_mispick.py`的`test_analyze_rejects_zero_offset`改成
  `test_analyze_accepts_zero_offset_as_identity`，確認`/api/mispick/analyze`用offset=0時
  nominal座標=實際座標，分類結果正確
- `mispick.js`的`nudgeOffset()`拿掉「算出0就強制改回±1」那段，方向微調現在可以正常停在0，繼續按
  同一個方向會正常變成-1(或+1)，不會卡住或跳過
- 表單欄位標籤從「機台偏移量（非0整數）」改成「機台偏移量（整數，0＝T點沒有偏移）」，預設值也從1
  改成0(符合「還沒量到偏移之前，狀態本來就是0」這個語意)
- 「①原始 wafer MAP」T點預覽區塊改成**同時畫兩張wafer圖**：左圖固定用手動輸入的T點座標本身(不套
  偏移，等於偏移量永遠是0的基準狀態)，右圖套用「3 偏移與BIN設定」目前選的機台偏移量，T點標記畫在
  `(手動輸入的T點X + dx, 手動輸入的T點Y + dy)`——`dx`/`dy`用跟`make_offset()`完全一樣的規則從
  axis/value換算(單軸，X填dx、Y填dy)，只是前端純視覺預覽用，不影響後端分析。改軸向、改偏移量數值、
  按方向微調按鈕，兩張圖(尤其右圖的T點位置)都會即時重畫，不用重新按「分析」
- 用Playwright實際操作驗證：預設偏移量是0、狀態文字顯示「目前偏移：無（0，T點沒有偏移）」、左右兩張
  圖T點都在同一格；把偏移量改成X+3後，左圖T點不動、右圖T點正確往右移3格；用方向微調按鈕從3連續往
  左按3次能精準停在0(不會被跳過)，再按一次正確變成-1

教訓：**跟這個專案其他好幾次教訓同一個模式——「一個值被程式拒絕」不代表這個值本身沒有意義，可能只是
最初設計時沒想到這個值該被允許。這次的0剛好是使用者操作邏輯裡最基本的基準狀態(沒有偏移)，卻被寫死
成不合法輸入，還連帶讓UI(方向微調按鈕)刻意繞開它——遇到使用者說「這個值應該要能選」時，值得先確認
這個限制本身有沒有真實依據，而不是預設它是刻意的安全防呆。**
